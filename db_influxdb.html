STEP 03 // LINE PROTOCOL & SERIES KEY

寫入時序數據：Line Protocol 語法結構與互動拆解

Line Protocol 標準語法公式（注意「逗號」與「空白鍵」的分隔位置）：
<measurement> , <tag_key>=<tag_value> ␣ 空白分隔 <field_key>=<field_value> ␣ 空白分隔 <timestamp>
目前檢視：投影片第 9 頁「生產統計表 PLC #1」範例（注意 PLC\ #1 使用反斜線跳脫空白）
production_stats,machine_name=PLC\ #1 feed=10i,discharge=8i,defect=2i,drill=5i,stamp=5i 1781258400000000000
欄位結構逐項對照表（點擊上方範例按鈕可切換解析內容）：
核心維度 1 // 有建立索引 (Indexed)

1. Series Key（序列鍵）＝ 核心索引

當寫入一行 Line Protocol 時，InfluxDB 會把 Measurement + Tags 的所有組合，在記憶體中封裝成一個個 Series Key。

machine_status + id=id_001 + machine_name=CNC_A01

底層原理：時序資料庫認為，同一個設備在不同時間點產生的數據，本質上只是同一個「序列 (Series)」在時間軸上的延伸。因此 Tags 適合放機台編號、感測器 ID 等用於分類篩選的文本。

核心維度 2 // 無建立索引 (Unindexed)

2. Fields（數據欄位）＝ 附屬的數值

如 feed_count=100i、defect_count=2i 這些 Field 數值，在底層是完全不建索引的。

[Timestamp 陣列] ⟷ [feed_count 數值陣列] / [defect_count 數值陣列]

底層原理：Fields 只是緊跟著 Timestamp（時間戳記主鍵）綁定在一起的陣列。這大幅省去了每次寫入時重建 B-Tree 索引的龐大開銷，讓每秒數萬筆的高速寫入成為可能。

STEP 04 // FLUX QUERY & PIVOT TRANSFORMATION

查詢並合併欄位：Flux 語法與 pivot() 轉置實戰

查詢近 90 天時序紀錄並展開欄位（管線運算子 |>） 

from(bucket: "production_data")
  |> range(start: -90d)
  |> filter(fn: (r) => r._measurement == "production_stats")
  |> pivot(rowKey: ["_time", "machine_name"], columnKey: ["_field"], valueColumn: "_value")
  |> sort(columns: ["_time"], desc: true)
  |> limit(n: 200)
from() & range(start: -90d)：指定從 production_data 儲存桶撈取過去 90 天內的資料（時序查詢必備時間範圍）。
filter(...)：篩選資料表 _measurement == "production_stats"。
pivot(...)：關鍵轉置函數！InfluxDB 預設會將每個 Field 拆成獨立小表顯示；透過 pivot 可將相同 _time 與 machine_name 的多個 _field 橫向展開合併成同一列。
sort() & limit(n: 200)：依時間由新到舊（desc: true）排序，並限制最多回傳 200 筆。

互動模擬：pivot() 前後資料表結構差異

已啟用 pivot()：同一個時間點與機台的所有感測器數值（進料、出料、不良、鑽孔、蓋印）完美合併成單一列寬表，方便報表呈現或匯出 CSV！

STEP 05 // INTERNAL ARCHITECTURE & STORAGE ENGINE

底層核心原理：TSM 儲存引擎、列式壓縮與三大設計思維

儲存引擎：TSM 樹 (Time Structured Merge-tree) 與 WAL 機制

為了應付工廠機台或感測器每秒幾萬筆的高併發寫入（High Write Throughput），InfluxDB 採用改良自 LSM-tree 的 TSM 引擎。點擊下方各階段查看底層流向：

STAGE 01 // 預寫日誌
1. WAL (Write Ahead Log)

資料一進來，先以「追加 (Append)」方式快速寫入硬碟 WAL 檔，確保突然斷電資料絕不遺失。

STAGE 02 // 記憶體表
2. MemTable (記憶體)

寫入 WAL 的同時，資料同步寫入記憶體中的 MemTable。當資料還在記憶體時，即可立刻被查詢到！

STAGE 03 // 刷盤 Flush
3. TSM 檔案 (永久儲存)

當 MemTable 滿了或達時間限制，會將記憶體數據序列化批量寫入硬碟，變成唯讀的 .tsm 檔案 (Flush)。

STAGE 04 // 背景壓縮合併
4. Compaction (壓縮合併)

後台程序定期把多個小 .tsm 合併成大 .tsm 檔案，自動剔除重複或已刪除數據並釋放空間。

目前檢視【1. WAL 預寫日誌】：隨機寫入硬碟非常慢，但「順序追加 (Sequential Append)」極快。WAL 讓 InfluxDB 兼顧記憶體等級的寫入速度與硬碟等級的斷電安全性。

傳統 MySQL：行式儲存 (Row-based)

I/O 讀取冗餘高

一整行資料不論型態（時間、整數、浮點數、文字）全部連續存在一起：

// 硬碟區塊連續排列方式：
[Row1: T1 | feed:100 | drill:50 | stamp:40] [Row2: T2 | feed:101 | drill:51 | stamp:41]

當你只想查詢「過去 30 天的進料次數 (feed_count)」時，傳統行式資料庫仍必須把整行裡的 drill_count 與 stamp_count 一併讀出，造成大量無謂的硬碟 I/O，且不同型態混放難以高效壓縮。

InfluxDB：列式儲存 (Column-based)

極致壓縮 + I/O 精準讀取

同一條 Series 的各個欄位在硬碟中分別存成獨立連續區塊：

Timestamp 區塊: [T1, T2, T3, T4 ...] → Gorilla 壓縮 (Delta-of-Delta >90%)
feed_count 區塊: [100i, 101i, 102i ...] ← 查詢時只精準讀取此列！
drill_count 區塊: [50i, 51i, 52i ...] （完全不需讀取，跳過 I/O）
1. 超高壓縮比：同列型態完全相同。時間戳記採用 Gorilla 演算法（計算前後時間差值的差值 Delta-of-Delta）壓縮率達 90% 以上；數值採用 Bit-packing / Float 壓縮。
2. 查詢極快：查 feed_count 時完全不碰 drill_count 或 stamp_count 的硬碟區塊，大幅降低硬碟 I/O。

InfluxDB 三大核心設計思維總結

理解時序資料庫與傳統關聯式資料庫（RDBMS）在設計哲學上的根本差異

PHILOSOPHY 01
寫入 > 讀取

為了應付每秒海量寫入，寧可先寫入記憶體（MemTable）與預寫日誌（WAL），背景再慢慢執行壓縮合併（Compaction）。

PHILOSOPHY 02
數據幾乎不修改

時序數據是「歷史紀錄」，發生了就不會變。因此不支援傳統的 UPDATE，只允許追加（Append）與同時間點覆寫。

PHILOSOPHY 03
時間是第一公民

所有數據都必須帶有時間（Timestamp），底層儲存、分割區塊（Shard）、保留策略（Retention Policy）全部繞著時間轉。
