1.1 探索視覺化開發的底層世界

Node-RED 提供了一個優雅的視覺化編程體驗，讓使用者可以藉由拖放節點、串接連線（Wires）來建構複雜 of 非同步應用。

然而，在流暢的 UI 背後，Node-RED 並不是一個簡單的腳本生成器，它本質上是一個事件驅動的 Node.js 執行期環境 (Runtime)。

在瀏覽器拖拉的視覺化圖形，會被轉為 JSON 拓撲結構，並最終由 Node.js 載入，以非同步事件模型在記憶體中執行。

1.2 Node-RED 的雙子星架構

Node-RED 架構主要由兩大核心部分組成，它們彼此獨立運作但緊密配合：

  • Editor (前端編輯器)：一個基於瀏覽器的單頁網頁應用 (SPA)，使用 jQuery、D3.js 提供視覺化編輯、配置與排版，並透過 API 與後端溝通。
  • Runtime (後端執行期)：執行在 Node.js 之上的伺服器，負責載入節點實體、執行流程邏輯、提供 HTTP API 與維持實時 WebSocket 同步。

🔗 連接兩者的橋樑：

HTTP Admin API 負責傳輸 Flow 的部署與操作指令，而 WebSocket (RED.comms) 則負責即時推送執行狀態（如 Debug 節點輸出、節點狀態標籤）。

1.6 EventEmitter 繼承關係

在 Node-RED 中，每個自訂節點物件在底層都不是孤立的。為了支援極致的事件驅動，所有的節點均繼承自基底類別 `Node`，而 `Node` 則繼承自 Node.js 原生的 `events.EventEmitter`。

這樣的原型繼承結構帶來了以下優勢：

  • 統一事件機制：節點可以監聽與觸發任何事件（例如 `'input'`, `'close'`）。
  • 極致解耦：Flow 引擎不需要關心節點具體做了什麼，飾面只向其發射 `'input'` 事件。
  • 高效執行：依賴 Node.js 的事件發射機制，完全運作於 V8 的高效事件通道上。

1.7 node.send() 的運作原理

當一個節點完成了它的處理邏輯，它會調用 `this.send(msg)`。這是 Node-RED 訊息傳遞的核心動力源。

`node.send` 內部的源碼執行邏輯如下：

Node.prototype.send = function(msg) {
    // 1. 取得該節點認領的 wires 連線映射
    const wires = this.updateWires || this.wires;
    if (!wires || wires.length === 0) return;
    
    // 2. 遍歷每一個輸出端口
    for (let i = 0; i < wires.length; i++) {
        const portWires = wires[i];
        if (portWires && portWires.length > 0) {
            // 3. 遍歷該端口連接的目標節點 ID
            for (let j = 0; j < portWires.length; j++) {
                const targetNode = RED.nodes.getNode(portWires[j]);
                if (targetNode) {
                    // 克隆訊息避免狀態污染，非同步/同步發送
                    const clonedMsg = RED.util.cloneMessage(msg);
                    targetNode.receive(clonedMsg);
                }
            }
        }
    }
};

1.8 事件監聽與 input 接收

在剛才的 `node.send()` 中，最後會呼叫目標節點的 `receive(msg)` 方法。這個方法是非同步投遞與事件觸發的轉折點：

其內部最核心的動作，就是觸發該節點的 `'input'` 事件：

Node.prototype.receive = function(msg) {
    if (msg) {
        // 觸發綁定的 input 事件監聽器
        this.emit("input", msg);
    }
};

而在編寫自訂節點時，我們最熟悉的建構函數內部，正是透過監聽此事件來實現邏輯：

function MyCustomNode(config) {
    RED.nodes.createNode(this, config);
    const node = this;
    
    node.on('input', function(msg) {
        // 在這裡撰寫該節點的核心運作邏輯
        msg.payload = msg.payload.toUpperCase();
        node.send(msg); // 處理完後，再次調用 send
    });
}

1.9 避免阻塞與 Event Loop

因為 Node.js 是單執行緒（Single-threaded）的，如果節點之間的 `node.send()` 到 `input` 事件完全是同步的遞迴呼叫，一旦 Flow 鏈條極長，便會帶來兩大問題：

  1. 呼叫棧溢出 (Stack Overflow)：過深的函數嵌套會耗盡 V8 的呼叫棧空間。
  2. 事件循環飢餓 (Loop Starvation)：執行緒一直被 JS 同步運算佔滿，導致網路 I/O、HTTP API 與 UI 更新無法及時回應。

🛡️ Node-RED 的安全邊界：

為了防止上述情況，Node-RED 在核心訊息路由時，有時會主動使用 `setImmediate()` 或是 `process.nextTick()` 將訊息的傳遞非同步化。這會讓出 JavaScript 呼叫棧控制權，讓 Event Loop 有機會去處理網路 I/O 與排程。

1.10 訊息流動三劍客：send、done 與 input

根據我們從 NotebookLM Mind Map.png 梳理的架構，Node-RED 應用層的訊息流動機制主要依賴三個最核心的機制來達成完整的協調：

  • `node.send(msg)`：訊息的推進器，負責複製訊息對象並將其路由投遞給下游的連線節點。
  • `node.done()`：任務回報與生命週期終點。在 Node-RED 1.0+ 之後，節點完成訊息處理後必須呼叫 node.done()，以便讓 Flows 引擎進行追蹤與資源清理，也是 Complete 節點觸發的依據。
  • `'input'` 事件 (異步事件回調)：節點核心邏輯的監聽點，當上游 `send` 過來時被發射。
這三劍客的協同，實現了資料從「輸入」到「背景計算」再到「生命週期終結與回報」的閉環運作。

2.1 JS 的單執行緒與非同步幻覺

大家都知道 JavaScript 是一門單執行緒 (Single-threaded) 的語言。這意味著在同一個時間點，主執行緒的呼叫棧只能執行一個任務。

那為什麼 Node.js 能夠同時處理上萬個高併發的網路 Socket 請求、或是在讀取檔案的同時還能響應 HTTP 服務？

💡 非同步的本質：

這是一個藉由「事件驅動」與「底層多執行緒協調」創造的幻覺。JS 主執行緒本身從不執行耗時的阻塞操作，而是將它們外包給作業系統內核或底層執行緒池，並在完成後以事件回呼的方式處理。

⏳ 任務時間軸交錯示意圖：

1

JS 主執行緒 (同步任務)

執行 JS 程式碼，發出非同步 `fs.readFile()` 請求 ──> **不等待結果，繼續執行後續代碼**。

2

底層(作業系統/執行緒池) (背景並行)

在背景實質執行硬碟 I/O，讀取檔案數據。主執行緒在此期間仍能處理其他 HTTP 請求。

3

回呼事件觸發 (Event Loop)

讀取完畢後，將 Callback 丟回 Event Loop 佇列。當主執行緒同步代碼執行完，Event Loop 撿起該 Callback 執行。

2.2 Node.js 的三層引擎架構

為了實現這種高效非同步調度，Node.js 內部架構由三層核心引擎緊密堆疊而成：

  • V8 引擎 (JS層)：Google 開源的高效 JS 執行引擎，負責將 JS 代碼編譯為機器碼並執行，管理 Call Stack 與 V8 堆積記憶體。
  • C++ Bindings (橋樑層)：Node.js 核心內建的 C++ 封裝，將 OS 級別的功能（如網路、檔案系統）包裝為 JavaScript API 提供給 V8 呼叫。
  • libuv (C語言層)：專門為 Node.js 開發的跨平台非同步 I/O 庫，負責管理 **Event Loop、Thread Pool、與 OS 非同步多路復用**。
Event Loop 的本質是由 libuv 在 C 語言層級實作的，它才是 Node.js 真正的非同步引擎心臟。

2.6 核心函數 uv_run 的定義

以下是 libuv Unix 平台上的 `uv_run` 的核心骨架代碼。它是由一個 `while` 循環構成，只要循環條件保持「活躍 (Alive)」且未調用 `uv_stop`，循環就會不斷執行：

int uv_run(uv_loop_t* loop, uv_run_mode mode) {
  int timeout;
  int r;
  int ran_pending;

  r = uv__loop_alive(loop);
  if (!r)
    uv__update_time(loop);

  while (r != 0 && loop->stop_flag == 0) {
    uv__update_time(loop);            // 更新時間
    uv__run_timers(loop);             // Timer 階段
    ran_pending = uv__run_pending(loop); // Pending I/O 階段
    uv__run_idle(loop);               // Idle 階段
    uv__run_prepare(loop);            // Prepare 階段

    timeout = 0;
    if ((mode == UV_RUN_DEFAULT && loop->stop_flag == 0) ||
        (mode == UV_RUN_ONCE && !ran_pending)) {
      timeout = uv__backend_timeout(loop);
    }

    uv__io_poll(loop, timeout);       // Poll 階段 (阻塞等待)
    uv__run_check(loop);              // Check 階段 (setImmediate)
    uv__run_closing_handles(loop);    // Close 階段

    r = uv__loop_alive(loop);
    if (mode == UV_RUN_ONCE || mode == UV_RUN_NOWAIT)
      break;
  }
  return r;
}

🕹️ uv_run_mode 模式說明：

  • `UV_RUN_DEFAULT`：預設模式。循環會一直執行，直到沒有活躍的監聽器。Node.js 啟動後就是使用此模式。
  • `UV_RUN_ONCE`：只執行一次 Poll。如果沒有 Pending 事件，會阻塞等待直到有第一個事件完成後執行，然後退出。
  • `UV_RUN_NOWAIT`：Poll 一下就立刻返回，不管有沒有事件，完全不阻塞。
這段 C 語言源碼就是 Node.js 事件驅動系統的心跳頻率。
2.7 解剖 uv_run：Timer 與 Pending

讓我們逐一拆解事件循環的各個階段。首先是每次循環最先觸發的 **Timer 階段**：

  • `uv__run_timers(loop)`：執行那些已經超時的計時器回呼（對應 JS 中的 `setTimeout` 與 `setInterval`）。
  • 最小堆積 (Min-Heap) 設計：在 libuv 中，所有的 Timer 是儲存在一個 Min-Heap 樹狀結構中。堆積頂部永遠是「最快過期」的計時器。這使得檢查是否有人過期只需 \(O(1)\) 時間，非常高效！

💡 Pending I/O 階段：

`uv__run_pending(loop)`：用來執行那些在上一輪 Poll 被延遲執行的 Pending I/O 回呼。例如，某些作業系統寫入 TCP Socket 成功後，回呼會先塞入 Pending 佇列，留待此時依序處理。

2.8 解剖 uv_run：Idle/Prepare 階段

在進入關鍵的 I/O Poll 阻塞等待之前，有兩個較為內部的輔助階段會被觸發：

  • `uv__run_idle(loop)`：雖然叫 "Idle" (空閒)，但它其實非常忙碌。一旦有活躍的 Idle handle，事件循環在每個 tick 都會同步呼叫它，主要用於核心內部性能分析或調試。
  • `uv__run_prepare(loop)`：顧名思義，它是進入 Poll 之前的準備工作。用來通知系統「我們馬上要進入阻塞監聽了」，進行部分資源快取更新。

⏱️ 計算 Timeout：

在進入 Poll 之前，libuv 必須計算出本次等待最長可以維持多久。計算規則如下： 1. 如果 loop 已經被呼叫 `uv_stop`，則超時為 0。 2. 如果沒有活躍的 handles/requests，超時為 0。 3. 如果有活躍的 Timer，則超時為「最近的 Timer 的過期剩餘時間」。這樣可以確保計時器能準時被喚醒！

⚙️ Timeout 決定邏輯：

// libuv uv__backend_timeout 簡化實現
int uv__backend_timeout(const uv_loop_t* loop) {
  if (loop->stop_flag != 0) return 0;
  if (!uv__loop_alive(loop)) return 0;
  
  // 如果有 Check handles (setImmediate)，不能在 Poll 阻塞，立刻返回
  if (loop->check_handles != NULL) return 0; 
  
  // 否則，返回最近的一個 Timer 的過期剩餘毫秒數
  return uv__next_timeout(loop); 
}
2.9 解剖 uv_run：I/O Poll 的等待

`uv__io_poll(loop, timeout)` 是整個事件循環最核心、也是唯一的阻塞等待點。

當 JS 沒有任何要執行的代碼時，執行緒會進入此函數，並呼叫作業系統的系統呼叫（如 Unix 的 `epoll_wait()`），進程隨之進入 Sleep 狀態，不佔用 CPU：

⚡ 喚醒執行緒的契機：

1. **網路封包到達**：網卡接收到 TCP 封包，產生硬體中斷，作業系統將 Socket 設為可讀，喚醒 `epoll_wait`。 2. **Timer 到期**：剛才計算 the timeout 毫秒數耗盡，核心發送時鐘中斷強制喚醒執行緒。 3. **執行緒池任務完成**：Worker thread 向主執行緒寫入管道訊號，喚醒 I/O Poll。

2.10 解剖 uv_run：Check 與 Close

在 Poll 階段被喚醒並處理完 I/O 事件後，事件循環會走入最後的清理路段：

  • Check 階段 (`uv__run_check`)：專門執行 Check handles 的回呼。在 Node.js 中，這對應著 **`setImmediate(callback)`**。
  • 由於 Check 階段緊鄰在 Poll 之後，因此在 Node.js 中，`setImmediate` 的回呼通常會比 `setTimeout(..., 0)` 更快響應新進的 I/O 事件！
  • Closing Handles 階段 (`uv__run_closing_handles`)：執行那些被關閉的 Handle 的 `close` 回呼。例如，當我們呼叫 `socket.destroy()`，對應的資源釋放回呼就在這個階段被執行。

⚙️ setImmediate (Check) 執行源碼：

// libuv uv__run_check 簡化實現
void uv__run_check(uv_loop_t* loop) {
  uv_check_t* h;
  QUEUE queue;
  QUEUE* q;

  // 將 Check 隊列移出來，避免在執行時動態修改隊列導致死循環
  QUEUE_MOVE(&loop->check_handles, &queue);

  while (!QUEUE_EMPTY(&queue)) {
    q = QUEUE_HEAD(&queue);
    h = QUEUE_DATA(q, uv_check_t, queue);
    QUEUE_REMOVE(q);
    
    h->cb(h); 
  }
}
2.11 特權插隊者：微任務 (Microtasks) 救護車與 Event Loop 公車

在事件循環的運作中，有一群擁有「特權」的插隊者，它們不屬於 libuv 的事件循環，而是直接受 V8 引擎管轄的微任務 (Microtasks)：

  • 微任務 (Microtasks) ── 救護車 🚑：
    • 代表：process.nextTick() (優先級最高) 與 Promise.then() (async/await)。
    • 特權：在目前 JavaScript 呼叫棧清空後，進入 Event Loop 下一個階段前，立刻強制清空所有微任務。
  • 宏任務 (Macrotasks) ── 公車 🚌：
    • 代表：setTimeout()、setImmediate()、I/O Callback。
    • 規則：必須按部就班，排隊等待事件循環轉到對應的專屬階段才能被撿起執行。

3.1 縱向漏斗式層次架構

要理解 Node-RED、Node.js 與 libuv 是如何協同工作的，最直觀的方法就是看一個具體的操作：在畫布中讀取本地檔案。

📁 架構穿透四部曲：

1. **Node-RED 應用層**：拉節點，傳入檔案路徑，啟動流程。 2. **Node.js 內核 API 層**：呼叫 `fs.readFile()` 轉化為非同步 C++ Binding 任務。 3. **libuv 調度層**：接收 C++ 任務，將阻塞的 File I/O 外包給 Thread Pool 執行，釋放主執行緒。 4. **OS 硬體層**：執行核心系統呼叫，操作硬碟，讀取磁區資料。

3.2 應用層：Node-RED 檔案節點

在最頂部的 **Node-RED 應用層**，所有代碼都是純粹的 JavaScript。以官方提供的 `File In` 節點為例：

當該節點收到 input 事件，其內部原始碼（`10-file.js`）核心邏輯如下：

const fs = require('fs');

node.on("input", function(msg) {
    const filename = node.filename || msg.filename;
    
    // 調用 Node.js 核心庫的非同步讀取檔案方法
    fs.readFile(filename, function(err, data) {
        if (err) {
            node.error(err, msg);
        } else {
            // 包裝讀取到的 Buffers/字串送至下一個節點
            msg.payload = data;
            node.send(msg);
        }
    });
});

🔍 應用層的特性：

  • 非阻塞回呼：Node-RED 傳入了一個匿名回呼函數 `function(err, data) { ... }` 作為 `fs.readFile` 的最後一個參數。
  • 同步調用返回：`fs.readFile` 被呼叫後會**立即返回**，主執行緒隨即解脫，可以去處理其他的事件，而不需要停下來等待磁碟轉動。
這層的本質是 JS 程式碼呼叫，它只負責宣告「我要讀這個檔案，讀完後請通知我的回呼函數」。
3.3 API 層：JS 核心包裝 fs.js

當 Node-RED 調用 `fs.readFile()`，呼叫就進入了 **Node.js 內核 API 層**。在 Node.js 的核心庫文件 `lib/fs.js` 中：

這個非同步 API 內部會執行參數校驗，並將其轉換成一個非同步任務物件。其內部偽代碼如下：

// Node.js lib/fs.js 內部源碼邏輯
function readFile(path, options, callback) {
  // 1. 校驗與格式化參數
  callback = maybeCallback(callback || options);
  
  // 2. 建立一個代表非同步檔案請求的 C++ 物件
  const req = new FSReqCallback();
  req.oncomplete = callback; // 將 JS 的 callback 綁定至 C++ 回呼
  
  // 3. 通過 C++ Binding 呼叫底層的 readFile
  const err = binding.readFile(path, req);
  if (err) {
    // 處理同步發生的錯誤
  }
}

⚙️ FSReqCallback 的核心作用：

  • 它是跨越 JS 與 C++ 的媒介。
  • 它把 JS 回呼函數的指針（記憶體地址）打包，保存在一個 C++ 結構中，隨後向下傳遞，確保底層讀完資料後能原路找回來。
`binding.readFile` 本質上是一個註冊在 V8 引擎中的 C++ 函數指針，它宣告了 JS 與 C++ 邊界的跨越。

3.5 V8 持久化指針：Persistent<Function> 的生命線

在非同步世界中，最致命的危機是「記憶體生命週期的錯位」。V8 引擎是如何保證回呼函數在數秒後依然存在？

  • 危機：Local Context 的銷毀
    當 fs.readFile 呼叫完畢後，JS 主執行緒的呼叫棧 (Call Stack) 會立刻清空。V8 引擎的 Local 作用域被銷毀，其內部的 JS 回呼函數變數將面臨被垃圾回收 (GC) 釋放的命運。
  • 解法：C++ Persistent 錨定
    C++ Bridge 接收到 JS 請求時，會將 JS 回呼函數包裝為 v8::Persistent<v8::Function>，強行保存在 C++ 堆積 (Heap) 中。
  • 此 Persistent 變數作為一個「記憶體錨點」，不受 V8 當前棧清空的影響。直到背景任務完工、回呼執行完畢後，C++ 才會調用 Reset() 釋放它，將控制權還給 V8 GC。

3.6 調度：libuv 的任務分流機制

現在任務來到了最底層的 **libuv**，這是事件循環真正大顯身手的地方。然而，libuv 在處理非同步時，會有一個關鍵的分流機制：

💡 異步分流的兩條路：

1. **非阻塞網路 I/O** (Sockets, Pipes)：作業系統本身提供了良好的非阻塞/多路復用 API（如 `epoll`）。因此，libuv 不需要用額外執行緒，直接將 Socket 描述符丟給 OS 監聽，完全由主執行緒管理。 2. **阻塞式系統操作** (檔案讀寫、DNS 查詢、Crypto 加密)：因為很多 OS 沒有良好的非同步檔案 I/O（檔案讀寫時，即使設定非阻塞，調用仍可能被硬碟尋軌阻塞）。為此，libuv 必須將它們**分流給執行緒池 (Thread Pool)**。

檔案讀寫 `uv_fs_read` 就走進了第二條路：執行緒池分流。

3.7 執行緒池 Thread Pool 原理

libuv 內部維護了一個全域的**執行緒池 (Thread Pool)**。預設情況下，這個池子包含 **4 個 Worker 執行緒**（可透過環境變數 `UV_THREADPOOL_SIZE` 最大擴展至 1024）。

執行緒池的運作遵循經典的**生產者-消費者模型**：

  • 主執行緒（生產者）將 `uv_fs_read` 任務包裝好，塞入 libuv 的全域任務佇列（Work Queue）。
  • 背景的 4 個 Worker 執行緒（消費者）通過互斥鎖（Mutex）競爭，領取佇列頭部的任務。

4.6 第四步：WebSocket (ws 套件) 與 RED.comms 廣播

    const packet = JSON.stringify({ topic: topic, data: data });

        if (ws.readyState === WebSocket.OPEN) {

    });

  • `ws.send()` 內部會處理 WebSocket 的掩碼（Masking）與訊框封裝。
  • 隨後，它會調用 Node.js 原生的 TCP 傳輸模組 `net.Socket.write()`，將資料塊投遞給底層。
這標誌著資料正式離開了 Node-RED 的純 JS 應用邏輯，準備進入 Node.js 核心與作業系統核心。
4.7 第五步：TCP Socket 寫入呼叫

在 Node.js 原生的 `lib/net.js` 模組中，`Socket.write()` 會處理寫入緩衝區，並透過 V8 C++ Bridge 呼叫 C++ Wrap 物件：

1

封裝為 Stream

JS 中的 TCP Socket 繼承自 `stream.Duplex`。`write` 會將 JSON 字串轉換成 binary 緩衝區 (Uint8Array)。

2

呼叫 C++ TCPWrap

呼叫 C++ Binding 中的 `TCPWrap`（定義在 `src/tcp_wrap.cc` 內），這是一個管理 OS Socket 的 C++ 類別。

3

呼叫 libuv C 語言寫入

`TCPWrap::Write` 接收二進位緩衝，打包為 `uv_write_t` 結構，並呼叫 libuv 的 `uv_write()` 方法。

📈 TCP Socket 寫入鏈條：

// JS 呼叫層級
net.Socket.write(data)
  └─> stream_base_commons.js: writev/writeUtf8
        └─> TCPWrap::Write (C++ class)
              └─> uv_write() (libuv C function)
4.8 第六步：C++ 封裝與 uv_write 的呼叫

在 libuv 中，`uv_write()`（定義在 `src/unix/stream.c` 或 `src/win/core.c` 內）是網路數據寫入的真正入口：

// libuv uv_write C 語言代碼簡化
int uv_write(uv_write_t* req, uv_stream_t* handle,
             const uv_buf_t bufs[], unsigned int nbufs,
             uv_write_cb cb) {
  // 1. 初始化寫入請求結構 req
  uv__req_init(handle->loop, req, UV_WRITE);
  req->cb = cb; // 保存 C++ 層的回呼指針
  req->handle = handle;
  
  // 2. 嘗試立即向 OS Socket 寫入資料
  int r = uv__try_write(handle, bufs, nbufs);
  if (r > 0) {
      // 如果全部資料已經一次性寫入完畢，直接返回，不用註冊事件！
      return 0; 
  }
  
  // 3. 若資料未發送完，將剩餘資料放入發送緩衝區，並註冊監聽
  uv__write_start(handle);
  // ...
}

🔍 核心決策：

  • `uv__try_write()`：試圖立即使用 `send()` 或 `write()` 系統呼叫發送。如果網路發送緩衝區未滿，這會非常快。
  • 非同步降級：如果發送緩衝區滿了，或者資料非常大無法一次性發出，則需要將 Socket FD 註冊到事件多路復用器（epoll/IOCP），進入非同步等待。
4.9 第七步：libuv I/O 多路復用註冊 (Windows IOCP)

因為我們是在 **Windows** 平台上執行，libuv 底層會調用 Windows 內核強大的 **IOCP (I/O Completion Ports)** 模型來完成這個任務：

1

建立完成埠關聯

當 Socket 建立時，呼叫 `CreateIoCompletionPort` 將 Socket 的 Handle 與 libuv 的完成埠關聯起來。

2

投遞 WSASend 請求

呼叫 Windows Socket 專屬 API `WSASend` 發送二進位封包。這是一個**重疊 (Overlapped) 異步操作**。Windows 核心接管發送任務，函數立即返回。

3

進入 OS 休眠

此時，主執行緒完成了 JS 任務，進入 Event Loop 的 `uv__io_poll`。它呼叫 `GetQueuedCompletionStatus` 在完成埠上休眠等待 OS 發送完畢通知。

4.10 第八步：作業系統通知、I/O 喚醒與 Event Loop callback 執行

當 Windows 核心完成網路資料包的實實發送，它會將一個「完成包（Completion Packet）」推入該 Socket 關聯的完成埠佇列中。

1

主執行緒被喚醒

`GetQueuedCompletionStatus` 收到完成包，主執行緒從休眠中被喚醒，收集到 TCP 發送完成事件。

2

放入 Pending Queue

libuv 將對應寫入請求的 `uv_write_cb` 回呼放入 Event Loop 完成佇列中，隨後執行，通知 C++ 寫入成功。

3

JS 層釋放與更新

回到 JS 層，`net.Socket` 觸發 `'drain'` 或執行寫入回呼。此時，WebSocket 資料幀已成功跨過網線，送到了使用者的瀏覽器。

⚙️ GetQueuedCompletionStatus 核心代碼：

// win/core.c uv__io_poll 簡化實現
void uv__io_poll(uv_loop_t* loop, int timeout) {
  // ...
  BOOL success = GetQueuedCompletionStatus(loop->iocp,
                                          &bytes,
                                          &key,
                                          &overlapped,
                                          timeout);
  if (success) {
    // 獲取 C 語言請求結構，並處理回呼
    uv_req_t* req = uv_overlapped_to_req(overlapped);
    uv_insert_pending_req(loop, req);
  }
}
4.11 實戰警示：不要阻塞事件循環 (Don't Block the Event Loop)

Node-RED Runtime 是一個單執行緒實體。這意味著：若其中任何一個 Flows 中的 Function 節點卡死，整個 Node-RED 都將同步凍結！

致命阻塞三大兇手：
  1. 同步 CPU 耗時計算：例如大陣列排序、高強度加解密、大數據統計。
  2. 同步 I/O 呼叫：在節點中呼叫 fs.readFileSync() 等同步 API。
  3. 大 JSON 同步解析：對數十 MB 的資料執行 JSON.parse(huge_string)。

後果：整個系統 of Event Loop 停擺，導致前端顯示「Connection Lost」、WebSocket 斷開、所有的 Flows 暫停運作、甚至 HTTP 請求超時。

🛡️ 阻塞代碼與非阻塞最佳實踐

錯誤示範 (卡死執行緒)
// 同步解析超大 JSON
const data = JSON.parse(hugeJSON);
msg.payload = process(data);
node.send(msg);
推薦做法 (非同步切片)
// 使用 setTimeout 讓出控制權
setTimeout(() => {
  const data = JSON.parse(hugeJSON);
  msg.payload = process(data);
  node.send(msg);
}, 0);
