Vibe Coding

速度與直覺

由 Andrej Karpathy 等人推廣的新世代編程哲學：開發者不再逐行敲打代碼，而是透過人機協同、意圖引導（Prompting）、審查即時結果與微調，在「心流（Vibe）」中極速落實想法。

優勢： 邊際開發成本趨近於零，數分鐘內立體化 Demo。
陷阱： 易陷入「代碼膨脹」、「忘記為誰而做」的局部最佳解。

Opportunity Solution Tree

方向與驗證

由產品探索名師 Teresa Torres 提出。四層結構：Outcome (商業成效) → Opportunities (客戶痛點/機會) → Solutions (可能解法) → Experiments (假設驗證)。

優勢： 避免「愛上第一個想法」，以嚴謹邏輯對齊目標與多樣解法。
傳統瓶頸： 傳統開發中，驗證每個解法的 Prototype 耗時費力。

產品路線圖如何演進？（從「產出導向 Output」到「成效導向 Outcome」）

第一代：功能清單甘特圖 (圖一)

承諾在 Q3 上線「自動同步」、Q4 上線「CRM 整合」。問題在於一旦市場變化或假設錯誤，團隊無法停止開發，造成巨大工程浪費。

第二代：OST 機會驅動圖譜 (圖二)

路線圖不再寫滿死板的功能名稱，而是寫上「要解決的用戶機會點」與「欲達成的核心指標」。多個 Solution 是並行假設，誰能達成指標就上線誰。

第三代：OST + Vibe Coding 敏捷共舞

在現代 AI 時代，路線圖的每個「實驗 (Experiment)」都能用 Vibe Coding 於半天內長出活體原型。高階路線圖保持戰略穩定，底層解法以 AI 光速輪轉迭代！

背後注入的 System Prompt

模擬就緒 
// ==========================================
// 產出：IEC 61131-3 結構化文字 (Structured Text)
// 專案：氣壓缸循序進退與夾爪控制
// ==========================================
PROGRAM CylinderSequence
VAR
    Step : INT := 0;
    Timer_2s : TON;
END_VAR

// 急停安全互鎖 (EMG Check)
IF NOT X2 THEN
    Y0 := FALSE;
    Y1 := FALSE;
    Y2 := FALSE;
    Step := 0;
    RETURN;
END_IF;

CASE Step OF
    0: (* 待機狀態：檢查原點 *)
        IF X0 THEN
            Step := 10;
        END_IF;

    10: (* 步驟 1：氣壓缸 A 前進 *)
        Y0 := TRUE;
        IF X1 THEN
            Y0 := FALSE;
            Step := 20;
        END_IF;

    20: (* 步驟 2：夾爪閉合 *)
        Y1 := TRUE;
        Step := 30;

    30: (* 步驟 3：延時 2 秒確認到位 *)
        Timer_2s(IN := TRUE, PT := T#2S);
        IF Timer_2s.Q THEN
            Timer_2s(IN := FALSE);
            Step := 40;
        END_IF;

    40: (* 步驟 4：氣壓缸 A 退回原點 *)
        Y2 := TRUE;
        IF X0 THEN
            Y2 := FALSE;
            Step := 0; (* 完成循環 *)
        END_IF;
END_CASE;
; ==========================================
; 產出：指令表 (Instruction List)
; 專案：氣壓缸循序進退與夾爪控制
; ==========================================
LD    X2            ; 載入急停信號 (常閉接點)
NOT
JMPC  EMG_STOP      ; 若急停觸發跳轉停止

LD    Step
EQ    0
AND   X0            ; 檢查是否在原點
JMPC  GOTO_STEP10

STEP10:
LD    TRUE
ST    Y0            ; 啟動前進閥門
LD    X1            ; 前進到位極限開關
JMPC  GOTO_STEP20

STEP20:
LD    TRUE
ST    Y1            ; 夾爪電磁閥閉合
CAL   TIMER_TON     ; 呼叫計時功能塊
LD    Timer_Done
JMPC  GOTO_STEP40

STEP40:
LD    FALSE
ST    Y0
LD    TRUE
ST    Y2            ; 啟動後退閥門
LD    X0
JMPC  GOTO_READY

EMG_STOP:
LD    FALSE
ST    Y0
ST    Y1
ST    Y2
RET
[初始步 00] 原點檢測 (感測器 X0=ON)
↓ 轉換條件：按下啟動按鈕 且 急停(X2)=正常
[步進 10] 氣壓缸 A 前進 (輸出 Y0=ON)
↓ 轉換條件：前進極限到位 (X1=ON)
[步進 20] 夾爪閉合夾取 (輸出 Y1=ON) 並啟動計時器 (T#2S)
↓ 轉換條件：Timer.Q 延時時間到達 (2秒)
[步進 30] 氣壓缸 A 後退 (輸出 Y2=ON, Y0=OFF)
↓ 轉換條件：返回原點 (X0=ON)
循環結束回到 [初始步 00]

Standard Operating Procedure

四步閉環實踐工作流

如何在日常迭代中無縫穿梭於架構思考與自然語言編程。

PHASE 01

成效與痛點錨定

先不開編輯器。定義單一核心 Outcome（如：D7 留存率提高 15%），並列出從用戶訪談中收斂出的 2~3 個核心 Opportunities。

產出：明確的樹狀主幹
PHASE 02

發散多重解法

針對每個痛點，腦力激盪出至少 3 個差異化解決方案（Solutions）。不要先入為主只選自己直覺想做的那一個。

產出：分岔的解法枝葉
PHASE 03

Vibe 原型暴擊

把 Solution 的假設打包成具備 Context 的 Prompt，丟給 AI 在 15 分鐘內生成出「可互動的最小實驗原型 (Experiment Prototype)」。

產出：可操作的網頁/功能 Demo
PHASE 04

驗證修枝與深化

將原型帶給 3~5 位真實用戶測試。若假設不成立，果斷剪除該枝條（Pruning），將心力轉向下一個 Solution，完全零情感負擔。

產出：經過驗證的生產代碼規劃

Prompt Engineering Templates

專為 OST 設計的 Vibe Coding 提示詞架構

告別「幫我做一個登入頁」這種低維度指示，用高維度語境引導 AI 給出最符合商業與痛點架構的代碼。

範本 01 發散解法階段

OST 機會點 → 多解法頭腦風暴

當你確定了用戶痛點，但希望 AI 同時從 UI、自動化、心理學等維度提供多種技術解法。

// 提示詞範本

我目前的目標 Outcome 是 [填入目標]，發現的用戶痛點 Opportunity 是 [填入痛點]。

請擔任資深產品架構師，針對此痛點提供 3 種截然不同的前端互動解決方案：
1. 低認知負荷型 (極簡引導)
2. 高度自動化型 (AI代勞)
3. 遊戲化反饋型 (即時獎勵)

並列出每個方案最脆弱的「核心假設 (Assumption)」。
範本 02 極速建構階段

單一解法 → 活體高傳真原型

鎖定某個特定解法後，要求 AI 用單一 HTML 或現代前端框架直接生成可點選的驗證原型。

// 提示詞範本

我們要驗證解法：[解法名稱與邏輯]。
請以 Vibe Coding 模式，直接在單一 HTML 檔案中產出可運行的極致高傳真原型。

規格要求：
- Tailwind CSS 現代精緻風格 (深色模式)
- 必須包含 Mock 互動狀態與轉場動效
- 埋入關鍵操作的點擊計數器 (用以驗證假設)
- 不要用假字 (Lorem Ipsum)，全部填入真實模擬情境數據。
範本 03 驗證修枝階段

原型測試回饋 → 程式碼重構修枝

收集到用戶真實反應後，以批判性視角要求 AI 分析為什麼成效不彰，並在原代碼上快速重構。

// 提示詞範本

我們在用戶測試中觀察到：[測試反饋，例：用戶在第 2 步因為字太多直接跳出]。

這代表我們先前的假設 [原假設] 失敗了。
請針對這段代碼進行敏捷重構：
1. 將文字指引改為微視覺動效提示
2. 將步驟從 3 步壓縮為 1 步點擊
3. 保留原有數據追蹤邏輯，輸出修改後的乾淨代碼。

避免 Vibe Coding 的五大「自嗨陷阱」

✕
陷阱 1：沉迷於微調絢麗動畫，忽略根本沒人要用

對照 OST：檢查這個動畫到底是為了解決哪個 Opportunity？如果只是滿足工程師的審美樂趣，請立刻停手。

✕
陷阱 2：生成了 10 個小功能，但主流程支離破碎

對照 OST：樹狀圖要求單一 Outcome。每一個功能都必須能追溯回頂層指標，否則會讓產品淪為「功能怪獸」。

✕
陷阱 3：捨不得刪除 AI 寫得很好的代碼 (沉沒成本謬誤)

對照 OST：記住，AI 寫代碼的邊際成本為零。只要驗證未達標，請豪邁按下 Delete，修剪樹枝才是產品負責人的真本事。
