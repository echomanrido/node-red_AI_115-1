實作交給執行團隊，人組成決策團隊

執行團隊 (Agent Team)
實作 測試 除錯 第一輪 Review
決策團隊 (People Team)
  • 決策： 技術選型、架構方向與取捨
  • 理解工程： 跟上 AI 的產出，抓住影響大的地方
  • 探索工程： 帶著 AI 找更好的可能
方向 ➔ 人給 AI 成果 ➔ AI 產給人
Slide 33 Prototype Phase Gate

原型期守住三個關卡，幾乎不看程式碼

Agent 的產出只需流過三個檢查哨。三關卡住，AI 就不會錯得太離譜：

1 驗證 (Verification)

怎麼證明它是對的： 自動測試機制、驗收指標與邊界測試。

2 介面 (Interface)

模組之間的約定： 前後端協議、API 規範、資料傳遞格式鎖死。

3 Use Case (情境)

我們要怎麼使用它： 真實端到端場景與關鍵使用路徑定義。

適用於原型快速迭代期。人類只看這三個關卡與 AI 整理出的高影響改動。
Slide 34 Core Principles

AI Native 公司要注意的三件事

組織層級的架構進化與角色重新定位：

1. 拆分執行與決策團隊（各司其職）
Agent Team：執行 People Team：決策
2. 好的 Agent 執行團隊要素
  • 持續運行、被優化、會學習
  • 容易和人對齊、隨時看得懂目前狀態
3. 人的核心課題
  • 定義目標： 對標市場、客戶、成果
  • 合作模式： Scope 大幅拆開來合作
  • 能力轉變： 學會全盤理解系統
核心認知轉變： 重心從「親手做」，變成持續對齊、持續決策。AI 替你實作，人反而要更懂整個專案！
01

第一層次：一個人怎麼用好 AI？

從單純把對話框當作解題工具，進階到 Coding Agent 時代；在規格驅動（Spec-Driven）中，我們最容易踩到什麼盲點？

真實血淚教訓：5,000 行 Spec 陷阱

在開發即時語音聊天模型專案時，團隊花了一個月詳述 5,000 行包含所有細節與範例的規格書，滿心以為交付給 Agent 就能一步到位。結果 LLM 的 Context 嚴重被瑣碎細節淹沒，連基本模組都啟動失敗。

核心警惕： Context 必須聚焦！過度冗長的規格會導致注意力發散，喪失任務主軸。

破局心法：Spec 是「鷹架」不是「藍圖」

藍圖是「窮盡細節、照圖施工」；而鷹架是「輔助結構立起來的暫時工具」。當建築本體（高品質代碼與介面）立起來之後，鷹架就應被收掉。

破局作法： 拆解大系統為獨立子模組（Submodules），逐一立起、確立 Interface，優質代碼本身就是對 AI 最好的引導。

大老思想碰撞：規格派 vs 原型派 (Prototype)

規格派 (Spec-Driven) 代表：Matt

利用「提問對齊」技巧，讓 AI 一問一答直到與人類語意完全對齊，才產出規格。適合任務目標具體、可清晰描述的邏輯系統。

優點：規格寫好後，生成期間人類可以去喝咖啡。
原型派 (Prototype-First) 代表：Boris (Cursor)

不耗時寫 Spec，直接下 Prompt 快速做出第一版 Prototype，看著原型邊測邊改。適合需求模糊、難以用言語精確描述的探索型專案。

特點：原型本身就是最真實的 Spec。
02

第二層次：一個人如何駕馭一群 AI Agent？

進入多 Agent（Agentic）工作流，人類面臨的最大威脅不是技術不足，而是淪為 Agent 流程中的「審批雜工」。

痛點：認知負荷與審批打工

AI 頻繁在終端回傳「要選 A 還是 B？」或生成冗長的 Review 報告。人類只能坐在螢幕前機械式狂按「同意」，注意力完全被瑣事佔用。

陷阱：強推看板管理造成二次負擔

嘗試讓 AI 自行領 Ticket 並移動看板，結果耗費了破億 Token，Agent 依舊會在非核心流程上出錯。因為「管理看板」對 Agent 也是額外負擔。

第一性原理：只監控，不微觀管理

讓 Agent 專心撰寫代碼；人類建立儀表板監控狀態與脈絡。需要時再透過 Tmux 終端 Attach 進去進行精準介入。

系統協調的核心燈塔

統一語言與架構紀錄 (DDD 思維)

AL Agents 規範
context.md（領域詞彙表）

確立專案中的通用名詞定義。例如清楚規範：Meta Agent 僅負責調度指揮，不直接動代碼；Member Agent 專注實作任務。代碼命名與商業領域名詞嚴格一致。

ADR (Architecture Decision Records)

記錄重大的技術架構決策與邊界理由。當 Agent 自主運行遇到分歧時，主動索引 ADR 即可自動判定最優解，不必頻繁打擾人類。

03

第三層次：AI-Native 公司的協作範式

AI Native 團隊不再是「人帶著工具寫代碼」，而是徹底劃分為**「執行團隊」**與**「決策團隊」**。

全自動化生產線

執行團隊 (全部由 AI 掌管)

  • 實作代碼編寫： 按照已拆解的 Submodule 快速產出。
  • 單元與整合測試： 自動產生測試並執行變異測試 (Mutation Testing)。
  • 除錯與細緻重構： 處理繁瑣的型別替換與流程化修改，不犯低級疏失。
弱點：容易陷在細節泥淖，缺乏跳脫框架看到「第三條路」的能力。
人類無可取代的護城河

決策團隊 (人類工程師的核心)

  • 架構決策與取捨： 跳脫 A/B 假兩難困局，給出更簡潔的架構路線。
  • 理解工程： 掌握全盤系統拓撲，指導 Agent 往對的方向開展。
  • 探索工程： 透過 Prototype 進行 A/B 版本快速試錯，提煉關鍵經驗。
守住三道關卡：驗證機制、模組介面 (Interface)、使用情境 (Use Case)。

演講金句總結

① Spec 如鷹架

規格是蓋程式時的輔助，結構一旦穩固就該收掉。高質量的 Code 與明確介面才是最強引導。

② 擺脫審批雜工

別讓 AI 頻繁丟 A/B 選項或搬看板分散精力。以儀表板宏觀監控，保留高階思考頻寬。

③ 品味與判斷力

AI 在雜訊與發散組合中徘徊，唯有人類清晰的眼光、品味與決策，能為系統指引第三條出路。
