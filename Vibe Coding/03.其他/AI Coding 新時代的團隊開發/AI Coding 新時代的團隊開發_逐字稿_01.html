AI Coding 團隊開發的三個演進層次（Three Levels of AI-Era Development）

陳宜昌（YC）指出：過去講團隊開發是「一群人的合作模式」，現在則是「一群人 ＋ 一群 AI Agent」的協作。隨著規模從個人擴大到整個公司，Spec 的角色、監控工具與人類職責都發生了根本轉變：

層次一 (Level 1) 1 Human + 1 AI

一個人怎麼使用 AI

  • 1.規格先行 (Spec-First)：動手寫 Code 前先對齊規格。
  • 2.測試驅動開發 (TDD)：用自動化測試驗證 AI 產出。
  • 3.照顧好 LLM Context：避免 5,000 行巨型 Spec 造成失焦。
💡 核心心法：把 Spec 當作「鷹架 (Scaffolding)」而非「藍圖」，模組蓋完即拆；好的程式碼本身才是可驗證的最強 Guiding。
層次二 (Level 2) 1 Human + N Agents

一個人怎麼用 Agent Team

  • 1.無重疊拆單：人定大架構，AI 拆單確保零耦合（前後端/模組分離）。
  • 2.DDD 系統燈塔：用 /grill-with-docs 維護 context.md (統一詞彙表) 與 ADR (架構決策紀錄)。
  • 3.零額外負荷監控 (oat-agents)：不逼 AI 移看板，改用 TUI 觀察脈絡、Worktree + Pod 隔離、tmux 介入。
💡 核心心法：老闆不要微觀管理！讓 Agent 專心做事，人只要觀察並看見資訊脈絡（或配一個助理 Agent 幫你看員工電腦並匯報）。
層次三 (Level 3) N Humans + N Agents

AI Native 公司的組織分工

  • 1.執行團隊 (100% AI)：負責實作、單元/整合/變異測試、除錯與 Review，人不寫程式碼。
  • 2.決策團隊 (Human)：負責架構決策、理解工程、探索工程。
  • 3.人際協作鎖死三關卡：驗證 (Verification)、介面 (Interface)、使用情境 (Use Case)。
💡 核心心法：AI 只會「做 (Output)」，不代表會產生「成果 (Outcome)」。弔詭的是：AI 幫你實作了，人反而更要理解全局！
實戰教訓一｜TASTE 2 語音聊天機器人 (00:07:50 – 00:14:25)

為什麼花一個月寫 5,000 行完美 Spec 卻徹底失敗？

在與台大李宏毅教授團隊合作將 ICLR 2026 TASTE 語音文字對齊模型推進至第二代即時串流語音聊天機器人時，工程複雜度飆高（Batch 轉 Streaming、中文化、對話後訓練、非同步多使用者、GPU 動態 Batching 調配）。

❌ 失敗做法：把 Spec 當「藍圖 (Blueprint)」

團隊三人花了整整一個月來回討論，寫出 5,000 行以上的主規格書＋大量測試範例 Reference，照顧到所有 Edge Case。結果交給 AI 生成後，連最基礎的 Module 都跑不起來——因為 5,000 行細節塞爆並稀釋了 LLM 的 Context，導致嚴重失焦。

✅ 成功做法：把 Spec 當「鷹架 (Scaffolding)」＋拆解模組

回歸軟體工程拆問題：拆成 3 個獨立 Submodules ＋ 1 個 Orchestrator。每個 Submodule 的 Spec 極小化，早上 1 小時就跑通第一個能用的 Submodule；接著 AI 直接讀取已完成的 Submodule 程式碼與 Interface，花 1–2 天就把複雜的 Orchestrator 串接完成！

實戰教訓二｜Noopher AI 的 Agent Team 演進四部曲 (00:23:24 – 00:32:22)

從「按同意的小弟」與「10 億 Token 看板流」到開源 oat-agents

v0
人工盯場時期：「我是服務 Agent 的小弟嗎？」

拉 GitHub Issue ➔ Plan ➔ 按同意 ➔ Work ➔ 按同意 ➔ Review (單元/整合/Spec/變異測試) ➔ 按同意。人類被綁在電腦前做制式確認。

v1
Claude Code 原生 Subagents：單一主視窗「洗版」

主視窗當 Meta Agent 調度 Planner / Worker / Reviewer + Git Worktree。平行度極高，但去上個廁所回來，Agent 提問被洗版洗到上面，痴痴停著等人類，人類認知負荷過高。

v2
看板流 (Kanban Flow)：一個月燒 10 億 Tokens 仍搞不定

規定 Agent 領單、寫思路、移看板（Backlog / To Do / Review）。結果學習看板規則造成 AI Agent 額外認知負荷，分散了寫程式的能量。

v3
第一性原理：開源 `oat-agents` (MIT License)

不需看板微觀管理，只需「監控員工電腦」！1 個 Meta Agent + 一群 Member Agents，原生 Claude Code / Codex 零額外負荷，結合 Git Worktree + Pod 隔離 + TUI 狀態/成本面板 + tmux 隨時登入 + 助理 Agent 匯報。

AI Native 公司組織設計：執行團隊 vs. 決策團隊（00:34:52 – 00:41:38）

比較維度 🤖 執行團隊 (Execution Team — 100% AI 主控) 🧠 決策團隊 (Decision Team — 人類負責)
核心定位 如同自動化生產線持續運行、可被優化、從中學習，負責把事情「做完 (Output)」 定義目標（對標市場、對標客戶、對標成果 Outcome），決定怎麼派工給執行團隊
具體職責 • 程式碼實作（人不寫程式碼）
• 單元測試、整合測試、Spec Review
• 變異測試 (Mutation Testing)（如把 < 改 > 檢查紅燈）
• 除錯與機械式、跨檔案型別修改 		1. 技術決策與架構取捨：跳脫 A/B 二選一框架，找出第三條路
2. 理解工程 (Comprehension Engineering)：借助 AI 掌握十萬行系統全局
3. 探索工程 (Exploration Engineering)：基於原型快速做 A/B/C/D 版實驗與外部資訊整合
人際協作三關卡 在鎖死邊界內自由平行產出程式碼，透過 context.md 與 ADR 燈塔自主對齊 人與人 Scope 切開，只鎖死三個關卡：① 驗證 (Verification)、② 介面 (Interface)、③ 使用情境 (Use Case)
海外路線分歧一｜00:14:47 – 00:17:09

究竟要先寫 Spec，還是直接做原型（Prototype）？

規格派 (Spec-First) Matt Pocock ↗

Matt Pocock (`/grill-me` Skill)

透過 /grill-me 讓 AI 像面試官一樣不斷追問你問題，把決策樹的每個分支都問到你跟 AI 100% 對齊後，才把 Spec 寫出來並交給 Agent 開發。

✅ 優點：Spec 寫完後，中間跑的過程可以放著去喝咖啡，省下盯場時間。
⚠️ 痛點：AI 講的語言跟人類有落差，前期討論與理解 AI 思維其實相當費力。
原型派 (Prototype-First) Boris Cherny ↗

Boris Cherny (Claude Code 創造者)

主張「不用寫 Spec，直接把原型做出來！」下 Prompt 先做第一版，測完有問題再改、持續迭代原型。原型出來後要嘛把細節修對，要嘛看著原型重做一份。「原型本身就是一個 Spec。」

✅ 優點：適合難以用文字事先描述的任務，免去前期痛苦的 Spec 對齊過程。
⚠️ 痛點：人必須一直坐在 Terminal 前面跟 AI 即時互動迭代。

海外路線分歧二｜00:17:10 – 00:19:13

AI 寫的程式碼又多又快，人類到底要看多少？

演講中比較了四位海外代表性開發者的觀點，收斂出共同趨勢：「少看逐行程式碼，多做高層次的監督與自動化驗證。」

Django 共同創造者

Simon Willison

一口氣讓 AI 產生程式碼，產生完之後「用 AI 去理解程式碼」——透過 AI 導覽（Walkthrough）的方式掌握結構，而非人工逐行硬啃。

AutoGPT 開發者

派工與驗收派

主張不要太去看程式碼！人類應該只管兩件事：AI Agent 要怎麼派出去（Dispatch），以及 AI Agent 產出要怎麼驗收（Acceptance）。

Rails 創造者 / Basecamp

DHH

依系統狀態決定看多少：若是新系統在打造原型（Prototype），全部不用看程式碼讓 AI 跑；若是 Basecamp 的複雜 Legacy Codebase，則必須看更多程式碼。

Vibe Coding 創造者

Andrej Karpathy

後期演講稍微改口修正：純粹不看 Code 的 Vibe Coding 比較適合用在「拋棄式專案」；若是真正的專業工程工作，仍必須做嚴格的監督與驗證。
