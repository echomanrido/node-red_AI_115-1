SDD 嚴格規格管線 Spec First

先定義 Schema 與 OpenAPI，由規格自動編譯出型別並迫使 AI 遵守邊界。

核心價值： 阻斷 AI 隨意更改資料結構引發的靜態型別錯誤。
BDD 行為轉譯管線 Story First

將 PM 與使用者的自然語言情境，透過三段式結構精準注入 AI 與 E2E 腳本。

核心價值： 消除 PM 與工程師、AI 之間的語意失真與理解偏差。
TDD 自修反饋閉環 Agentic Loop

AI 讀取測試紅燈報錯，在無人干預下自主修復實作代碼，直至綠燈全亮。

核心價值： 最適合 Cursor / Claude Code 自動執行任務的閉環基石。

三大驅動開發模式全剖析

理解規格 (SDD)、行為 (BDD) 與測試 (TDD) 的定位，打造駕馭 AI 的防護網。

Spec-Driven Development 系統結構與合約基石

規格驅動開發：用 Contract 先行束縛 AI 幻覺

SDD 強調在寫下任何實作代碼之前，先定義嚴格、具體的規格協議。這通常包括 OpenAPI (Swagger) 規範、TypeScript 介面型別、Protobuf 或 JSON Schema。

在 Vibe Coding 時代的角色：

AI 擁有極強的推導能力，但容易自行發明欄位名稱（例如有時用 `user_id`，下一次提示卻用 `accountId`）。提供 SDD 規格就像給予 AI 軌道，禁止其越界。

典型產物： openapi.yaml, types.d.ts, schema.prisma, GraphQL SDL
關鍵受益者： 前後端分離團隊、多 AI Agent 協同系統
AI 協同指令：「嚴格根據下方 OpenAPI 結構，只生成 handler 邏輯」
OpenAPI / Type Spec Example YAML / TypeScript 
components:
  schemas:
    PaymentOrder:
      type: object
      required: [orderId, amount, currency, status]
      properties:
        orderId: { type: string, format: uuid }
        amount: { type: integer, minimum: 1 }
        currency: { type: string, enum: [TWD, USD, JPY] }
        status: { type: string, enum: [PENDING, PAID, FAILED] }

# AI 任務：依此 spec 自動產生 DB Migration 與 Controller
💡 SDD 訣竅： 要求 AI 先審閱並輸出 Spec，經人類確認後，再下令「依據此規格進行代碼實現」。
Behavior-Driven Development 業務價值與場景故事

行為驅動開發：跨越商業語言與代碼的鴻溝

BDD 衍生自 TDD，但採用領域特定語言（例如 Gherkin 語法：Given-When-Then）來描述系統對使用者外顯的行為表現。BDD 的核心在於確保技術產出真正滿足商業意圖。

在 Vibe Coding 時代的角色：

Vibe Coding 很容易做出看似很炫、但根本不符合特定商業流程的玩具功能。Given-When-Then 是極具條理的 Prompt 範本，可精準告訴 AI 使用者情境與邊界條件。

典型產物： feature files (Cucumber / Behave), E2E Cypress/Playwright specs
關鍵受益者： 產品經理 (PM)、QA 團隊、終端客戶與 AI Agent
語法公式： Given (前提) ➔ When (觸發事件) ➔ Then (預期結果)
Gherkin Scenario Example .feature 檔案 
Feature: VIP 會員生日結帳折扣

  Scenario: VIP 會員在生日當月消費滿額獲得折扣
    Given 使用者為已登入的 "VIP" 會員
    And 當前月份為該會員的出生月份
    And 購物車總額為 1200 元
    When 使用者點擊進入「確認結帳」頁面
    Then 系統應套用 "生日 8 折" 優惠碼
    And 最終應付金額應顯示為 960 元
    And 發送「祝您生日快樂」推播通知
💡 BDD 訣竅： 把 Gherkin 腳本直接貼給 AI，要求它以 Playwright 或 Cypress 寫出可執行的端到端測試代碼。
Test-Driven Development 代碼品質與持續重構

測試驅動開發：打造 AI 最強的「自我修正反饋環」

TDD 依循嚴格的「紅燈 (Red) ➔ 綠燈 (Green) ➔ 重構 (Refactor)」微循環。先寫失敗的單元測試，再寫剛好能通過測試的極簡代碼，最後在測試保護下優化架構。

在 Vibe Coding 時代的超能力：

大語言模型天生具備「依據錯誤訊息修正代碼」的超強能力。當我們擁有自動化測試時，AI 可以在終端機內自跑測試、看報錯、自修代碼，形成無人值守的高效閉環！

典型產物： Jest, Vitest, PyTest, Go Test 測試套件
關鍵受益者： 模組架構師、重構人員、自主修復型 AI (Agentic Loop)
核心精神： 「未經測試的代碼即是有罪的 (Guilty until proven innocent)」
Vitest / Jest Unit Test TypeScript 
// 步驟 1: 先寫單元測試 (此時 calculateTax 甚至還不存在)
import { describe, it, expect } from 'vitest';
import { calculateTax } from './taxCalculator';

describe('calculateTax()', () => {
  it('當輸入小於或等於 0 時應拋出 InvalidAmountError', () => {
    expect(() => calculateTax(-50)).toThrow('InvalidAmount');
  });

  it('在台灣境內稅率 5% 應四捨五入到整數', () => {
    expect(calculateTax(105, 'TW')).toBe(5);
  });
});
💡 TDD 訣竅： 命令 AI：「請只編寫通過上述測試的最小實作代碼，嚴禁添加任何多餘邏輯。」

自建 BDD Skill 流程表
Skill 內容定義 (直接配置於 Agent 設定) Markdown Format 
# Custom BDD Skill for AI Agents
你是一個遵循嚴格 BDD (行為驅動開發) 的專家，依據指令執行相應模式：

## 指令集 (Commands)
- `/specify [需求]`:
  - 僅產出 Given/When/Then (Gherkin 格式) 驗收規格。
  - **嚴禁編寫任何實作程式碼**。
- `/bdd:scenario`:
  - 補齊正向路徑 (Happy Path)、極端邊界與錯誤處理。
- `/bdd:test`:
  - 將上述情境轉換為可自動執行的測試腳本 (Playwright / Vitest)。
- `/implement`:
  - 進行代碼實作，直到所有測試通過亮綠燈為止。
指令 作用
/specify [需求] 要求 AI 只生成包含 Given/When/Then 的驗收規格，不寫程式碼
/bdd:scenario 針對既有功能補充正向與邊界條件的 Gherkin 場景
/bdd:test 將上一步的 Given/When/Then 轉化為自動化測試腳本
/implement 執行測試驅動開發，直到所有 Scenarios 亮綠燈
支援 Cursor / Claude Code / Copilot Living Spec Guard

            SDD Prompt
            
          

          
規格至上合約提示詞

          
引導 AI 先行制定嚴格型別介面與 API 定義，確認後再實作邏輯。

          

            
你是一名資深系統架構師。在撰寫任何業務邏輯代碼前，請嚴格執行 SDD 流程：

1. 先輸出此功能所依據的 OpenAPI 3.0 YAML 或 TypeScript Interface 定義。
2. 列出所有欄位型別、必填狀態、列舉值 (Enums) 與邊界約束（如 min, max）。
3. 停下來等待我確認。確認無誤後，請嚴格依據該 Interface 生成 Server/Client 實作代碼，不可私自增減欄位。

          

        

        

          適合：前後端聯調、資料庫 Schema 變更。
        

      


      
      

        

          

            BDD Prompt
            
          

          
場景驗收 Gherkin 提示詞

          
將非技術性商業需求轉換為 Given-When-Then 自動驗收腳本。

          

            
你是一名 BDD 實踐專家。我有一個產品需求，請為我進行以下轉換：

1. 將需求拆解為至少 3 個 Gherkin 格式的驗收情境 (包含正常路徑 Happy Path、極端邊界與錯誤處理)。
2. 使用 Given / When / Then 語法明確描述上下文。
3. 為每個情境生成對應的 Playwright / Cypress 端到端測試骨架。
4. 確保業務人員也能輕易閱讀該情境說明。

          

        

        

          適合：使用者故事 (User Stories)、跨職能團隊驗收。
        

      


      
      

        

          

            TDD Prompt
            
          

          
紅綠重構自修循環提示詞

          
指示 AI 在終端機自我驗證，完成極致精簡且經過驗證的代碼。

          

            
我們遵循嚴格的 TDD (測試驅動開發)：

第一步 (Red)：請先編寫完整的單元測試檔案（覆蓋正常值、0、負數與空值），此時切勿編寫任何實作代碼。
第二步 (Green)：編寫最精簡的實作代碼，目的僅為讓上述測試 100% 通過。
第三步 (Refactor)：在確保所有測試全綠的前提下，重構代碼結構並提高可讀性。若測試失敗，請自我排查日誌直到全數通過。

          

        

        

          適合：核心算法、金流計算、Cursor / Claude Code Agent 迴圈。
