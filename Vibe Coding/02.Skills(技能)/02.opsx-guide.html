⚡ Spec-Driven Development (SDD)

OpenSpec 開發全生命週期解析

從「盤點問題」到「封存交付」，透過規格先行與可追溯工件，告別盲目 Coding 與 AI 規格漂移。本文檔完整梳理 5 大指令與各階段產生的關鍵檔案。

Step 01 /opsx:explore 盤點問題與釐清 Step 02 /opsx:propose 生成規格與工件 Step 03 /opsx:apply 按圖施工依序實作 Step 04 /opsx:verify 規格符合度驗證 Step 05 /opsx:archive 規格合流與封存
01

/opsx:explore 探索模式

盤點問題、釐清未知架構、評估可行性與劃定變更邊界

思考與發散階段

🎯 核心定位與操作理念

「在動手寫代碼或規格前，先徹底想清楚。」

使用者往往有模糊的需求概念或面臨棘手 Bug，此時不應直接盲寫代碼。`/opsx:explore` 是 AI 與工程師的高維度思維對齊階段，用於深入盤點系統既有邏輯、評估技術棧選型並定義邊界。

  • ✓ 釐清「為什麼做 (Why)」：挖掘真實痛點，避免無效開發。
  • ✓ 劃定「變更範圍 (Scope)」：確定哪些檔案受影響、哪些保留。
  • ✓ 識別架構盲點：事前發現潛在 Breaking Change 或資料庫遷移風險。
/opsx:explore 對話式觸發

📁 檔案變動與生成生命週期

產物：探索備忘與需求摘要 (Scratchpad)
📁 專案根目錄/ └── 📁 .agent/ (或臨時對話上下文中) └── 📄 scratchpad.md ← 記錄需求痛點、架構決策與邊界
對話記憶 / scratchpad.md 記錄探索結論，作為下一步 `/opsx:propose` 產出正式規格書的直接輸入原料。
02

/opsx:propose 寫出規格

規格先行！自動生成 4 大標準 OpenSpec 工件與原子化任務清單

規格化與工件產出

🎯 核心定位與操作理念

「規格即不可推翻的合約，按圖索驥的基石。」

將前階段探索出的結論，一次性沉澱為標準化的 OpenSpec 變更包（Change Proposal）。此階段產出完整設計、增量規範與詳細分解任務，絕不含糊。

  • ✓ Proposal：闡述問題背景、預期收益與架構邊界。
  • ✓ Delta Specs：明確用 ADDED / MODIFIED 規範模組能力。
  • ✓ Design：架構圖、資料結構、UI/UX 互動流程。
  • ✓ Tasks：分解為原子化 Checklists（如 1.1, 1.2...）。
openspec new change <change-name> CLI 實體指令

📁 檔案變動與生成生命週期

產物：openspec/changes/<change-name>/ 下 4 大工件
📁 openspec/changes/web-calendar-app/ ├── ⚙️ .openspec.yaml ← 變更元數據定義 ├── 📄 proposal.md ← 計畫書 (目標與風險) ├── 📄 design.md ← 技術設計與資料模型架構 ├── 📁 specs/ ← 各模組增量規格 (Delta Specs) │ ├── 📄 auth/spec.md │ └── 📄 calendar/spec.md └── 📄 tasks.md ← 原子實作清單 (- [ ] Checklist)
proposal.md & design.md 定義「為什麼做」以及「技術如何達成」的頂層設計文件。
tasks.md 包含未勾選（- [ ]）的完整實施計畫，為下一步 apply 的指揮中心。
03

/opsx:apply 依規格實作

按圖施工！以 tasks.md 為導航，逐項編寫程式碼並更新完成狀態

代碼實施階段

🎯 核心定位與操作理念

「精準實施，杜絕隨意發揮與程式碼飄移。」

AI 與開發者依據 `tasks.md` 裡的項目，以原子化步驟（Atomic steps）循序編寫 HTML、CSS、JS 與後端代碼。每完成一項任務，即刻在 `tasks.md` 標記為完成（`- [x]`），保證進度透明。

  • ✓ 遵循最小變動原則：嚴格依據 spec.md 寫代碼，不脫稿演出。
  • ✓ 任務即時回報：每項任務完成立即勾選，進度不遺失。
  • ✓ 隨時可中斷續行：若遇問題隨時停頓調整，支援中斷重啟。
openspec instructions apply --change <name> CLI 實體指令

📁 檔案變動與生成生命週期

產物：專案源碼實體建立與 tasks.md 狀態同步
📁 專案根目錄/ ├── 📄 index.html ← 建立/修改前端 UI 視圖 ├── 📁 styles/main.css ← 實作設計系統與元件樣式 ├── 📁 scripts/ ← 實作各模組業務邏輯 (CRUD/Sync) └── 📁 openspec/changes/web-calendar-app/ └── 📄 tasks.md ← 任務即時更新 (- [ ] → - [x])
原始碼檔案 (Source Code) 專案實際運行的程式檔案，完全依照 specs/ 規範打造。
tasks.md (狀態更新) 從 0/16 逐步推進至 16/16 全部勾選完成狀態。
04

/opsx:verify 對照驗證

品質守門人！對照規格書與任務驗收標準，執行語法與功能檢驗

驗收與測試把關

🎯 核心定位與操作理念

「確保每條 Requirement 都有對應的驗收與測試通過。」

在封存交付前，執行自動化語法檢查、規格合法性驗證（`openspec validate`）與進度狀態盤點（`openspec status`）。確認任務 100% 達成、無未捕獲異常且功能行為與預期無偏差。

  • ✓ 結構合法性驗證：確保 OpenSpec 格式無語法毀損。
  • ✓ 100% 完工確認：檢查 tasks.md 是否全部完成（state: all_done）。
  • ✓ 語法與回歸測試：執行 node --check 與相依性檢查。
openspec validate <name> && openspec status CLI 實體指令

📁 檔案變動與生成生命週期

產物：驗證通過訊號與 Walkthrough 驗收報告
📁 專案根目錄/ ├── 📄 walkthrough.md ← 產出實測成果與功能清單報告 └── 💻 Terminal Console ← 輸出：Change is valid (16/16 done)
walkthrough.md (驗證報告) 條列所有完成的功能亮點、測試結果與部署狀態，供團隊 Review 備查。
Valid Status (合規標誌) 確認符合封存標準，准許進入第五階段合流。
05

/opsx:archive 封存交付

主幹合流！Delta Specs 晉升為主規格，變更提案歸檔至歷史庫

合流與週期閉環

🎯 核心定位與操作理念

「讓規格成為系統的單一事實來源（Single Source of Truth）。」

當變更實施且驗證完畢後，執行 `/opsx:archive`。CLI 會自動把提案中的 Delta Specs 萃取並合併至全域主規格目錄 `openspec/specs/` 中，同時將提案搬遷至 `archive/YYYY-MM-DD-<name>`。工作區恢復乾淨，規格永久留存！

  • ✓ 主規格同步 (Master Sync)：增量需求正式成為主幹規範。
  • ✓ 變更目錄歸檔：按日期打標歸檔，歷史記錄完全可溯。
  • ✓ 清空作用中隊列：openspec list 回復乾淨狀態。
openspec archive --yes <change-name> CLI 實體指令

📁 檔案變動與生成生命週期 (關鍵轉移！)

產物：openspec/specs/ 主規格庫 + archive/ 封存歸檔
📁 openspec/ ├── 📁 specs/ ★ 萃取晉升為全域主規格庫！ │ ├── 📄 auth-and-profiles/spec.md │ ├── 📄 calendar-view/spec.md │ ├── 📄 data-persistence/spec.md │ └── 📄 task-management/spec.md └── 📁 changes/ ├── web-calendar-app/ ← 原始提案目錄被自動移動 └── 📁 archive/ └── 📁 2026-10-14-web-calendar-app/ ← 打上日期歸檔保存 ├── ⚙️ .openspec.yaml ├── 📄 proposal.md / design.md └── 📄 tasks.md (16/16 done)
openspec/specs/ (核心事實庫) 變更中的 Delta Specs 自動合流至此，成為日後維護與後續提案的參照基準。
openspec/changes/archive/ (歷史封存) 保留完整的當初思考提案、任務與實作歷程，任何時候皆可複盤。

📊 5 大階段全流程對照表

一覽各指令之目的、輸入依據、產出檔案與最終狀態轉變。

階段 對應指令 主要目的 依據來源 (Input) 生成 / 影響檔案 (Output) 完成標誌 (Outcome)
01. 盤點問題 /opsx:explore 釐清需求背景與技術可行性 使用者模糊想法、現有代碼 scratchpad.md (思維筆記草案) 確定「做什麼與邊界」
02. 寫出規格 /opsx:propose 產生標準化規格提案與任務清單 探索結論、架構決策 openspec/changes/<name>/ 下的 proposal.md, design.md, specs/, tasks.md 產出可執行的 Checklists
03. 依規格實作 /opsx:apply 按圖施工，逐步編寫代碼 specs/ 與 tasks.md 原始碼 (index.html, *.js, *.css) + tasks.md 勾選狀態 所有任務標記為 - [x]
04. 對照驗證 /opsx:verify 檢驗規格合規度與代碼品質 已完成之代碼與 Delta Specs walkthrough.md 驗證總結報告 Change is valid (100% 通過)
05. 封存交付 /opsx:archive 規格主幹合流與變更目錄封存 驗收通過的變更目錄 生成 openspec/specs/ 主規格庫 + 移動至 archive/YYYY-MM-DD-<name> No active changes 閉環交付
