UML 14 種圖表分類與介紹

統一塑模語言（Unified Modeling Language，簡稱 UML）在 UML 2.x 標準中共包含 14 種圖表（Diagram types），主要分為 結構圖（7種） 與 行為圖（7種，含互動圖 4 種），是精準引導 AI 架構理解的全球標準規範。

一

結構圖 / 靜態圖（Structural / Static Diagrams） 共 7 種 • 描述系統靜態結構、組成元件、類別與實體關係

AI 協作王牌 ★★★★★
1

類別圖 (Class Diagram)

核心功能：顯示系統的類別、屬性、方法（操作）以及類別之間的關聯（依賴、繼承、關聯等）。

Vibe 妙用：直接讓 AI 輸出 Prisma Schema、TypeScript Interface 或 Pydantic 資料模型，杜絕欄位幻覺。
Mermaid: classDiagram
2

物件圖 (Object Diagram)

核心功能：類別圖在特定時間點的實例（Instance）快照，呈現物件具體數值與當前狀態。

Vibe 妙用：提供具體 Mock Data 範例（如複雜 JSON Payload 或單元測試輸入數據）。
適用：測試案例資料模擬 ★★☆☆☆
3

元件圖 (Component Diagram)

核心功能：顯示軟體元件（模組、函式庫、微服務）與其對外暴露的介面、彼此依賴關係。

Vibe 妙用：規範 Monorepo、前端模組劃分，防止 AI 寫出循環依賴的失控引用。
適用：微服務與模組拆分 ★★★☆☆
4

複合結構圖 (Composite Structure)

核心功能：描述類別或元件內部的微型結構、零件（Part）、連接埠（Port）與協作關係。

Vibe 妙用：設計高複雜度中繼路由器或內部模組接腳（Ports & Adapters）。
適用：內部細部結構裝配 ★☆☆☆☆
5

部署圖 (Deployment Diagram)

核心功能：顯示硬體節點以及軟體元件在硬體環境（伺服器、Docker、雲端叢集）上的部署架構。

Vibe 妙用：讓 AI 一鍵產出精準的 Docker Compose、K8s Manifest 或 Terraform IaC 代碼。
適用：DevOps & IaC 自動化 ★★★★☆
6

套件圖 (Package Diagram)

核心功能：將系統的類別或其他元素分組管理，呈現套件與套件之間的層級與依賴關係。

Vibe 妙用：指示 AI 建立乾淨的目錄樹架構與依賴邊界（Clean Architecture）。
適用：目錄架構與職責邊界 ★★★☆☆
7

描述檔圖 (Profile Diagram)

核心功能：用來對 UML 進行擴充與領域特定客製化（自定義 Stereotypes、Tagged Values、約束條件 Constraints）。

Vibe 妙用：建立特定領域專用標記（如 Spring `@Service`、DDD `@AggregateRoot` 概念標記）。
適用：自定義擴充與 DSL 構建 ★☆☆☆☆

行為圖 / 動態圖（Behavioral / Dynamic Diagrams） 共 7 種 • 描述系統的動態行為、執行流程與時間順序

Vibe 妙用：專案開局時讓 AI 快速確認 MVP 功能邊界，防止需求無窮蔓延（Scope Creep）。

Vibe 妙用：精準控制 If/Else 決策路徑、使用者導引流程（Onboarding）與異常捕獲。

核心功能：描述物件在其生命週期內所經歷的各種狀態，以及如何因事件而轉換狀態。

Vibe 妙用：杜絕「未付款偷出貨」或「取消訂單還扣款」等非法狀態跳躍，打造強健狀態機。

2. 互動圖（Interaction Diagrams，行為圖的子類別，共 4 種 • 呈現物件/參與者之間的訊息傳遞與互動順序）

11
順序圖 / 時序圖 (Sequence)

核心功能：依「時間先後順序」呈現物件與參與者之間傳遞訊息的互動過程。

Vibe 妙用：徹底解決前後端 API 呼叫先後順序混亂、JWT 驗證跳過等重大時序失誤！
Mermaid: sequenceDiagram
12
溝通圖 (Communication)

核心功能：強調物件之間「連結與拓撲關係」的互動圖（舊版 UML 稱為協作圖 Collaboration Diagram）。

Vibe 妙用：用於檢查物件之間的結構耦合度，在重構複雜依賴關係時供 AI 參考。
適用：物件關係分析 ★★☆☆☆
13
互動概觀圖 (Overview)

核心功能：結合活動圖與順序圖，用來綜觀多個互動流程的宏觀控制邏輯與條件分支。

Vibe 妙用：宏觀串接多個時序子流程（例如：登入時序 ➔ 付款時序 ➔ 出貨時序）。
適用：高階時序宏觀串聯 ★★★☆☆
14
時間圖 (Timing Diagram)

核心功能：著重在「時間尺度」上，精確觀察物件狀態或具體數值的實時變化與時基約束。

Vibe 妙用：即時音視訊串流、音訊封包傳輸、硬體通訊協議驅動程式開發。
適用：硬體時脈與極限性能優化 ★☆☆☆☆

物件導向架構基石

類別圖的 6 大關係（Class Relationships）

在最常用的「類別圖」中，物件與類別之間常見 6 種關係。理解這 6 種關係在耦合強度（由弱到強）與生命週期依賴上的差異，能讓你在使用 Vibe Coding 時精準引導 AI 設計出符合物件導向原則與乾淨架構（Clean Architecture）的程式碼！

耦合度最弱（暫時性依賴） 關係依賴強度階梯 (由弱到強) 耦合度最強（生命週期緊密綁定）
1.依賴 2.關聯 3.聚合 4.組合 5.泛化/繼承 6.實現
強度：最弱 (Use-a) Mermaid: ..>

1. 依賴（Dependency）

定義：A 的變動會影響 B，屬於暫時性關係。常見於方法參數傳入、區域變數或靜態方法調用。

// 程式碼特徵：作為方法參數
class OrderController {
checkout(service: PaymentService) {}
}
Vibe 提醒：避免長存欄位，指示 AI 透過依賴注入（DI）解耦。
強度：弱至中 (Has-a / Knows-a) Mermaid: -->

2. 關聯（Association）

定義：類別之間長期且具備知名度的連結。A 類別通常將 B 類別作為成員變數保存。

// 程式碼特徵：長期成員變數引用
class Teacher {
students: Student[];
}
Vibe 提醒：定義 Prisma 或 TypeORM 的一對多、多對多關係模型。
強度：中等 (Weak Whole-Part) Mermaid: o--

3. 聚合（Aggregation）

定義：整體與部分的關係，但部分可以獨立於整體而存在（空心菱形）。整體解散，部分仍完好。

// 部門解散，員工依然存在
class Department {
constructor(public members: Employee[]) {}
}
Vibe 提醒：資料庫設定 `ON DELETE SET NULL`，不隨父級直接被連鎖刪除。
強度：強 (Strong Whole-Part) Mermaid: *--

4. 組合（Composition）

定義：強烈的整體與部分關係（實心菱形），部分隨整體的誕生而生、隨整體的毀滅而亡。

// 訂單被刪除，訂單項目隨之消亡
class Order {
items = [new OrderItem()];
}
Vibe 提醒：在 Prisma Schema 必須要求 AI 配置 `onDelete: Cascade` 連動刪除。
強度：極強 (Is-a) Mermaid: <|--

5. 泛化 / 繼承（Inheritance）

定義：親子類別關係（空心三角形箭頭指向父類），子類別繼承父類別的屬性與方法，實現程式碼重用與多型。

// 子類別繼承父類別
class AdminUser extends BaseUser {
grantSuperAdminRole() {}
}
Vibe 提醒：要求 AI 善用 BaseEntity 抽象基類，統一宣告 id、createdAt 等欄位。
強度：合約實現 (Can-do) Mermaid: ..|>

6. 實現（Realization）

定義：類別實作介面（Interface）所定義的操作契約（虛線空心三角形箭頭指向介面），是物件導向抽象的核心。

// 類別實作 Interface
class StripeGateway implements IPaymentGateway {
charge(amount: number) {}
}
Vibe 提醒：依賴反轉原則（DIP）的關鍵！指示 AI 依賴介面而非具體實體。

                                    模板一：混亂代碼 ➔ 逆向轉成 UML
                                

                                
                            

                            

                                接手別人（或前幾天 Vibe 出來）的一千行混亂程式碼？用這段 Prompt 請 AI 自動畫圖幫你整理架構：
                            

                            
請仔細分析以下程式碼，不要直接重構。
請執行下列兩步驟：
1. 繪製標準 Mermaid sequenceDiagram（時序圖），梳理出前端請求、服務層、資料庫與外部依賴的互動全流程。
2. 繪製 Mermaid classDiagram，歸納主要實體模型（Entity）與函式介面。
3. 點出代碼中缺乏防禦、可能造成記憶體洩漏或狀態混亂的架構漏洞。

[貼上混亂代碼]

                        

                        

                            適用情境：專案重構、接手遺留系統、Code Review
                        

                    


                    
                    

                        

                            

                                

                                    
                                    模板二：.cursorrules / System Prompt 規範
                                

                                
                            

                            

                                將此段加到你的專案 `.cursorrules` 或 AI System Prompt 中，強制 AI 先設計再寫代碼：
                            

                            
【架構優先設計原則 (Spec-First Architecture)】
在為此專案生成任何多檔案新功能前：
1. 必須先以 Mermaid 繪製簡短 UML 狀態圖或時序圖，確認資料流向與邊界狀態。
2. 保持元件單一職責（SRP）。若牽涉非同步狀態，需明確定義 Loading / Success / Error 狀態機。
3. 確認架構獲我同意後，才開始編寫代碼。代碼變數命名必須與 UML 圖形中的命名 100% 嚴格一致。

                        

                        

                            適用情境：Cursor Rules、Windsurf Workflows、Claude Project Instructions
