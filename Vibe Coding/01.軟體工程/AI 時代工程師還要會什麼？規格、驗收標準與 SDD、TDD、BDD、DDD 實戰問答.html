AI 時代工程師還要會什麼？規格、驗收標準與 SDD、TDD、BDD、DDD 實戰問答

📘 核心價值公式
工程師價值 ＝ 企業重視（貼近營收） ∩ 市場稀缺性

當 AI 讓「寫出程式碼」變得廉價（稀缺性趨近於零），唯有往上游移動到「定義規格、驗收標準、複雜技術決策」才能維持高薪與不可替代性。

💡 生活化比喻（ELI5）

蓋房子比喻：以前工程師是稀缺的「泥作師傅（寫 Code）」，現在 AI 是速度 10 倍的 3D 建築機器人。工程師別跟機器人比砌磚，而要轉型成懂施工細節的「建築師＋驗屋師」——因為你親手砌過磚（寫過 Code），畫出來的藍圖（規格）與驗屋清單（自動化測試）才不會天馬行空、無法落地！

複雜技術決策（最上游 · 極高稀缺）

投資建議：最高優先

由於 LLM 的注意力有限、容易在跨系統權衡時出現盲點或幻覺，複雜的技術選型、跨平台解耦與邊界條件權衡，仍必須由具備實戰底蘊的工程師最終拍板。

⚠️ 悲觀現實：別再死守下游

Junior 與純切版/純寫 Code 職缺急劇萎縮，公司越來越傾向找 FDE 或全端工程師。當 AI 寫 Code 速度是你的 10 倍時，花時間精進手寫語法的投資報酬率已大幅降低。

🚀 樂觀護城河：可落地的抽象能力

工程師憑什麼做 PM 的事？因為你寫過 Code，定規格時腦袋裡同步浮現 Data Model、API Model 與自動化測試邊界。一旦工程師走到上游，幾乎沒人能跟你競爭！

Part 2 · 00:14:53 – 00:21:10

SDD、TDD、BDD、DDD 差別在哪？本質都是「拆解 LLM 注意力」

點擊流程圖任一階段連動說明
🔥 關鍵破題：這四個 D 裡面，只有 SDD 不是方法論！
TDD、BDD、DDD 都是累積 10～20 年文獻、解決重複痛點的嚴謹方法論；而 SDD（Spec-Driven Development）本質只是把 Spec 一次塞給 AI 後「祈禱拜拜」。因此，TDD / BDD / DDD 在 AI 時代的實戰目的，就是拆解 LLM 注意力（Attention），大幅拉高 Spec → Code 的可靠度！

SDD（Spec-Driven Development）— 規格驅動開發

Spec → Code（祈禱拜拜）

單純把需求規格寫清楚後一次餵給 AI 產出程式碼。它本身不是嚴謹方法論，因為中間缺乏驗證關卡，LLM 一次處理太多脈絡容易眼高手低。適合「導入期」快速驗證，但成長期後必須疊加 TDD/BDD。

名詞 是否為方法論 工作流程 在 AI 時代解決的核心痛點
SDD 否（市場名詞） Spec → Code 取代零散對話 Prompt，但缺乏驗證，靠祈禱拜拜。
TDD 是 Spec → Test → Code 加入自動化測試：驗證 AI 正確性＋回歸保護既有程式碼。
BDD 是 Spec → Gherkin → Test → Code 避免 AI 連 Test 都寫錯；用白話 Gherkin 對齊 PM 與 RD。
DDD 是 Domain Model 輔助 Spec 統一跨部門語言（Ubiquitous Language），減少認知落差。
Part 3 · 00:21:11 – 00:23:38

Agent Skill（別只叫 SKILL.md）：用模組化 Prompt 落地全自動工作流

📦 正名：Agent Skill 是一個 Package（資料夾）

單一檔案裝不下複雜工程知識，所以才需要用資料夾將指令、規範、範本與腳本封裝成「模組化的 Prompt」。

🧩 新手拆分法則：一個產出物 ＝ 一個 Skill

以最簡 SDD 為例：Skill 1 專門追問需求、寫好寫滿規格；Skill 2 專門將規格轉為程式碼。投資時間打磨專屬 Skill，能在整個職涯持續產生複利！

範例：AI-BDD Gherkin 行為規格（連 PM 都看得懂的驗收標準） 
Feature: 核心門檻功能保護（Kano Threshold）
  Background:
    Given 專案已進入「成長期」且具備既有付費用戶

  Scenario: 實作新需求時不得破壞既有核心功能
    Given 系統已建立「結帳金流」與「筆記儲存」的自動化回歸測試
    When AI Agent 根據新需求修改程式碼
    Then 所有既有的自動化測試必須 100% 通過
    And 架構審查 Evaluator Skill 不得回報嚴重耦合（Bad Smell）

步驟 1：選擇產品生命週期
步驟 2：選擇功能類型（Kano Model）
建議策略：AI-BDD / TDD（Test-First 嚴格保護）

Part 5 · 00:35:01 – 00:44:27

Code Review 新思維（Evaluator Skill）與企業導入實戰

🩺 為什麼要 Code Review？為了切除架構「腫瘤」

Review 源自 Trust Issue，但千萬別逐行人工看！真正的目的是防止架構長出「腫瘤」（越長越大、無法維護，還會以訛傳訛讓團隊照抄錯誤寫法）。

  • 第一步：做 Pattern Matching，列出你在意的 Bad Smell（解耦、跨平台、效能）。
  • 第二步：寫成專屬 Evaluator Skill。
  • 第三步：用 Worker Agent 寫 Code ＋ Evaluator Sub-agent 吃 Skill 嚴格審查，直接省下 90% 審查時間！

🏢 怎麼說服公司導入？看對象給「具體成效」

  • 對 PM（讓事情變簡單）：給他一個會自動追問的 Skill，輕鬆產出能落地的 Gherkin 規格，自然不會排斥。
  • 對工程師（別談規格，談自動化測試！）：工程師有派系且懷疑規格價值；讓他們看到「上萬個自動化測試在背景跑 5～6 小時、看 AI 表演」，自然就會加入。
  • 最大阻力＝業務團隊：連董事長都不敢動賺錢的業務。解法是靠科技而非強迫學 Skill——讓業務照舊開工單，由 AI 幫他們補齊後端溝通。
Part 6 · 00:44:28 – 00:55:06

打破穀倉效應：DDD 統一語言、Shared Context 與「認知超前」

❌ 治標不治本：Local 端 1-on-1 對話（穀倉效應）

每個人的 Context 鎖在各自終端機 Session 裡，Jira 規格過時沒同步，導致 AI 被誤導、產生嚴重「認知負債」。不導入共享上下文，怎麼優化個人 Prompt 都無法根治。

✅ 根本解法：GitHub Repo Shared Context（認知超前）

以 GitHub Repo 作為單一事實來源（Single Source of Truth），PM 率先當責並學會用 Git 開 Plan；每次討論完就讓 Agent 把關鍵決策（Decisions）寫回共享 Context，AI 就能跨會議、跨程式碼、跨專案自動串聯洞察！

範本：Shared Context 決策紀錄（存入 GitHub Repo / docs/decisions/） 
# Plan: 2026-Q4 訂單結帳重構
- **當責人 (Owner)**：PM（規格與 Glossary 一致性檢查）＋ RD（實作交付確認）
- **Ubiquitous Language (Glossary)**：
  - `Order`：已成立之交易單（不可與 `Cart` 混用）
- **關鍵決策流水帳 (Decisions Log)**：
  1. [2026-11-26] 跨平台共用核心結帳規則，抽離至 `domain/checkout`，禁止直接依賴前端框架。
  2. [2026-11-26] 所有 Session 討論出的邊界條件，結束前必須由 Agent 寫回本檔並提交 PR。
Part 7 · 00:55:07 – 01:07:55

雙模型智商分配：高智商管「測試與架構審查」，避開 Self-Bias
