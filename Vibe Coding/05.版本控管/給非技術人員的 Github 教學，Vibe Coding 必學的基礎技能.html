情境引入：Gary 的記帳軟體 Vibe Coding 惡夢

假設你用 Claude Code 或 Cursor 做出了一個超好用的記帳 App，但當你叫 AI 「幫我加一個統計圓餅圖」時，原本好好的記帳按鈕突然壞掉了！你沒有留存檔點，只能硬著頭皮叫 AI 猜測修復；更慘的是，當朋友想幫忙一起開發時，你們還在用壓縮檔傳來傳去——這就是你必須學會 Git 與 GitHub 的原因。

CHAPTER 01

基礎雙雄：GitHub 與 Git 到底差在哪？

很多人一開始會把 Git 和 GitHub 混為一談。其實它們是兩個分工明確的工具，一個住在雲端網路，一個住在你自己的電腦裡：

🔵 核心觀念對照
☁️ GitHub ＝ 程式碼專用的 Google Drive

一個雲端網站平台。用來存放你的專案備份（稱為 Repo / Repository 倉庫），讓你在不同電腦都能存取，也能設定權限邀請朋友一起協作修改。

💻 Git ＝ 本機電腦裡的「時光機監控系統」

安裝在你電腦裡的版本控制工具。透過 git init 初始化後，它會默默盯著專案資料夾裡的每一個檔案變化，隨時記錄「誰在什麼時候改了哪一行」。

版本狀態數學抽象： 初始化後的專案可視為一連串時間快照集合 $\mathcal{H} = \{S_0, S_1, S_2, \dots, S_n\}$，其中每一個狀態 $S_i$ 都完整保存了該時間點的程式碼目錄結構。
🟢 給 AI 的白話指令：啟動本機版本追蹤

「請幫我檢查這個專案是否已經初始化 Git，如果還沒，請幫我執行 git init 並建立一個初步的版本記錄。」

CHAPTER 02

存檔、資安紅線與協作循環

從自己電腦存檔到上傳雲端，再到朋友下載協作，總共有五個核心動作。在數學上，本機與雲端的同步可表示為狀態轉移映射： $$S_{\text{local}} \xrightarrow{\text{commit}} S_{\text{snapshot}} \xrightarrow{\text{push (filtered by .gitignore)}} S_{\text{remote}} \xrightarrow{\text{clone / pull}} S_{\text{teammate}}$$

互動圖解 1

本機與雲端流向模擬器

目前步驟：1. git init 初始化
1. git init 初始化： 在你的本機專案資料夾裡建立一個隱藏的 .git 追蹤系統。從這一刻起，電腦裡所有的檔案修改都會被納入監控，但還沒有存檔，也還沒連上雲端。
🔴 資安紅線警告：Push 前務必檢查 .gitignore！

Vibe Coding 時常會用到 OpenAI、Claude 或資料庫的 API 金鑰（通通放在 .env 檔案裡）。如果你在 push 上傳到 GitHub 之前沒有設定好 .gitignore（忽略清單），你的 API Key 就會被公開在網路上，幾分鐘內就會被駭客爬蟲盜刷到破產！一旦不小心推上去，就算事後刪除紀錄也來不及，唯一的解法是立刻去後台把那把金鑰作廢重辦。

🟢 每次 Push 前必下的保命 Prompt：
🟡 新手常見兩大誤區
  • 誤區一：以為 commit 就是上傳雲端？ 錯！commit 只是像玩單機遊戲打魔王前的「手動存檔點」，檔案還在你電腦裡；必須再做一次 push（推送至 origin main），檔案才會真正飛到 GitHub 雲端。
  • 誤區二：叫朋友直接按網頁上的「Download ZIP」？ 千萬不要！下載壓縮檔只會拿到死板的檔案，完全失去了 .git 版本追蹤能力，以後無法用 pull 同步更新。一定要用 clone（複製）才是正式加入協作！
CHAPTER 03

「神奇辦公桌」：Branch 分支 vs Worktree 多工作區

在 Git 世界裡，預設有一條代表「穩定正式版」的主線叫做 main。當你要開發新功能時，直接在 main 上面改非常危險——萬一 AI 改壞了，連原本能用的版本都沒了！這時就需要 branch（分支） 和進階神技 worktree（多工作區）。

互動圖解 2

神奇辦公桌切換器：單桌平行時空 vs IKEA 買第二張桌

單一辦公桌 (main 主線)： 就像你書房裡的一張神奇辦公桌，桌面上正攤開著正式上線的穩定版程式碼。
為什麼多 AI Agent 開發要用 worktree？ 如果只有一張桌子（單純 branch），兩個 AI 同時改檔案會互相覆蓋檔案系統；透過 worktree 開出多個實體工作目錄後，平行開發總耗時從序列相加縮短為最大值： $$T_{\text{worktree}} = \max(T_{\text{Agent A (資料庫)}},\; T_{\text{Agent B (UI 設計)}}) < T_{\text{Agent A}} + T_{\text{Agent B}}$$
🟢 給 AI 的白話指令：開分支與開多工作區

「我要開發新的圓餅圖統計功能，請先幫我從 main 開一條新的 branch 叫做 feat-chart，不要直接改到 main。」

「我想要同時開另一個 AI 視窗來改 UI 介面，請幫我用 git worktree 在旁邊建立一個新的獨立工作資料夾並切到 feat-ui 分支。」

CHAPTER 04

審核合併（PR & Merge）與 Conflict 衝突決策

📬

1. PR (Pull Request) ＝ 合併申請單

當你在 feat-chart 分支把新功能測試好並 push 到 GitHub 後，可以發起一個 PR。它就像一份「變更報告」，把這次改了哪些程式碼列出來，方便你或團隊夥伴檢查確認沒問題。

🤝

2. Merge ＝ 正式合併回 main 主線

審查通過後，在 GitHub 按下綠色的 Merge pull request 按鈕，新功能就會正式融入雲端的 main 正式版！

🟡 關鍵提醒：你的本機電腦不會「通靈」！

當你在 GitHub 網頁上按下 Merge 後，只有「雲端」的 main 更新了，你電腦裡的 main 並不會自動感應同步！記得回到你的 AI 編輯器，叫 AI 幫你「切回 main 分支並執行一次 git pull」，這樣本機才會拿到最新的合併成果。

🔵 遇到 Conflict（程式碼衝突）怎麼辦？非技術人員的解決心法

當你跟朋友（或兩個不同分支）剛好改到了「同一個檔案的同一行程式碼」，合併時 Git 會跳出 Conflict（衝突），請人類決定要聽誰的。在數學上，若兩筆變更集在相同檔案位置產生交集衝突（$\Delta A \cap \Delta B \neq \emptyset$），AI 工具通常會用三種策略幫你處理：

策略 1：二選一

保留其中一邊的版本，直接捨棄另一邊（例如：「保留我改的新版按鈕，捨棄舊的」）。

策略 2：兩邊都保留

如果兩邊都是新增不同功能，只是剛好寫在同一處，就上下都保留下來。

策略 3：重寫整合

請 AI 讀懂兩邊的意圖後，重新寫一段完美融合兩者功能的新程式碼。

💡 Gary 的心法： 你不需要看懂紅紅綠綠的衝突符號！你只要以「產品經理」的角度告訴 AI 你的產品決策（例如：「我希望按鈕是藍色的，而且點擊後要跳出確認視窗」），AI 就會自動幫你修好所有衝突。

🟢 給 AI 的白話指令：發起 PR 與解決合併衝突

「目前合併發生了 Conflict 衝突。我的產品需求是：保留新版的圓餅圖統計功能，同時也要保留原本的匯出 CSV 按鈕。請幫我依這個邏輯解決所有衝突並完成合併。」

CHAPTER 05

AI 改壞程式怎麼救？Restore vs Revert

Vibe Coding 最常遇到的就是「AI 改過頭把整個畫面弄壞了」。這時候千萬別慌張叫 AI 盲猜修復，只要判斷一個問題：「你剛剛 commit（存檔）了沒？」 就能精準時光倒流！

互動圖解 3

AI 改壞程式救援決策器

請點選你目前的慘況，觀察時間軸如何安全還原：

git restore（一鍵讀檔）： 因為你還沒執行 commit，這堆改壞的程式碼只是暫存的草稿。執行 restore 會直接把所有未存檔的修改丟掉，瞬間回到上一個正常存檔點 C2，就像遊戲死亡後直接讀取上一個存檔！
為什麼協作時要用 revert 而不是硬刪歷史？ revert 的本質是產生一筆與錯誤提交 $C_{\text{bad}}$ 大小相等、方向相反的逆向變更 $C_{\text{revert}} = -C_{\text{bad}}$，使得最新狀態滿足： $$S_{\text{new}} = S_{\text{C2}} + C_{\text{bad}} + C_{\text{revert}} = S_{\text{C2}} + \Delta 0 = S_{\text{C2}}$$ 這樣既能讓程式恢復正常，又能完整保留「曾經改錯又修好」的歷史軌跡，不會讓協作夥伴的電腦產生歷史衝突。
🟢 給 AI 的白話指令：一鍵救援還原

「剛才的修改把程式弄壞了！請幫我檢查這批改動是否已經 commit：如果還沒 commit，請用 git restore 幫我全部還原到上一個存檔點；如果已經 commit 了，請幫我用 git revert 產生一筆反向提交來抵消剛才的錯誤。」

▶ 00:00:00 基礎概念

開場引言：Vibe Coding 的痛點與 GitHub 雲端倉庫

哈囉大家好，我是 Gary。最近越來越多非技術背景的朋友開始使用 Cursor 或 Claude Code 進行 Vibe Coding，只用自然語言就能做出自己的網站或記帳軟體。但大家很快就會遇到兩個超痛苦的問題：第一，當你叫 AI 增加新功能時，它不小心把原本好好的舊功能改壞了，你卻不知道怎麼退回上一步；第二，當你想找朋友一起合作開發專案時，難道每次都要把資料夾打包成 ZIP 壓縮檔用 LINE 傳來傳去嗎？

這就是為什麼我們今天要學 GitHub。對非技術人員來說，你不需要去背任何工程師的黑色終端機指令，只要聽懂背後的觀念，就能直接用白話文叫 AI 幫你操作。你可以把 GitHub 想像成「程式碼專用的 Google Drive」，它是一個放在雲端的平台，每個專案在上面都叫做一個 Repository（簡稱 Repo，倉庫），它不僅能幫你把心血安全備份在雲端，還能記錄每一次的修改歷史並支援多人同時協作。

🔵 核心精華： GitHub = 雲端專案倉庫（Repo）。就像在 Google Drive 建立雲端資料夾一樣，讓程式碼不再只困在單一一台電腦裡。
▶ 00:01:56 基礎概念 / 存檔

本機追蹤系統 Git、git init 與 Commit 遊戲存檔點

了解雲端的 GitHub 之後，那什麼是 Git 呢？Git 是安裝在你自己電腦（本機端）裡的一套版本控制工具。當你在電腦裡建立好記帳軟體的資料夾後，第一步就是要請 AI 幫你執行 git init（Initialize 初始化）。這個動作就像是在你的資料夾裡裝了一台隱形監視器，從這一秒開始，裡面任何一個檔案新增、修改或刪除，Git 都會幫你盯得死死的。

接著，當你請 AI 寫出第一版能正常記帳的畫面後，千萬不要急著繼續改！你應該先做一個動作叫做 commit（提交存檔）。你可以把 commit 想像成玩單機 RPG 遊戲、準備走進魔王房間前的「手動存檔點」。你會寫一句簡單的存檔備註，例如「完成基礎記帳輸入介面」，Git 就會把此刻完美的狀態拍成一張快照存在你電腦的隱藏資料夾裡。要特別注意的是，commit 只是存在你自己的電腦裡，這時候 GitHub 雲端上還完全看不到東西喔！

狀態轉移模型： 每次執行存檔皆是將當前工作目錄狀態 $S_t$ 與變更集 $\Delta_t$ 封裝為不可變的歷史節點：$$S_{t+1} = \text{commit}(S_t, \Delta_t)$$
🟢 給 AI 的實戰指令：「目前這個版本測試沒問題，請幫我執行 git commit 存檔，備註寫『完成基礎記帳畫面』。」
▶ 00:04:21 存檔與資安

Push 推送上雲端，以及絕對不能踩的 .gitignore 資安紅線

在本機做好 commit 存檔後，接下來我們要把這個進度送到雲端的 GitHub 倉庫（通常預設雲端位置叫做 origin main），這個「上傳」的動作就叫做 push（推送）。一旦你執行 git push，你在本機存檔的程式碼就會正式同步到 GitHub 網站上。

但是！在執行 push 之前有一個超級重要的保命動作，大家一定要畫三顆星星：檢查 .gitignore！ 我們在做 Vibe Coding 時，經常會串接 OpenAI、Claude 或雲端資料庫，這些付費的 API 金鑰（API Keys）與密碼通常會放在一個叫做 .env 的環境變數檔案裡。.gitignore 就像是一份「忽略清單（黑名單）」，凡是寫在 .gitignore 裡面的檔案，Git 在 push 的時候就會自動跳過、不准上傳。

如果你忘記把 .env 放進 .gitignore 就把專案推上公開的 GitHub，網路上隨時都有駭客的自動爬蟲機器人在掃描新上傳的程式碼，不到幾分鐘你的 API 金鑰就會被盜用刷爆帳單！而且就算你事後發現趕快把檔案刪掉，Git 的歷史紀錄裡還是留有痕跡，唯一補救辦法只有立刻去服務商後台把那把金鑰作廢重辦。所以每次 push 前，務必請 AI 幫你確認 .env 已經被安全排除！

🔴 資安鐵律： 公開上傳集合必須滿足過濾條件 $F_{\text{remote}} = F_{\text{local}} \setminus F_{\text{gitignore}}$，且確保 $\{ \texttt{.env},\; \texttt{*key*} \} \subseteq F_{\text{gitignore}}$。一旦金鑰外洩，唯有「作廢舊金鑰」才能止血！
▶ 00:06:07 多人協作

告別壓縮檔！多人協作循環：Clone 與 Pull

當你的專案已經安全 push 到 GitHub 之後，現在你的朋友想加入一起開發，該怎麼做呢？千萬不要叫他去 GitHub 網頁點「Download ZIP」下載壓縮檔！因為下載壓縮檔只會拿到死板的檔案，裡面完全沒有 .git 的版本追蹤大腦，未來你們沒辦法互相同步更新。

正確的做法是把專案網址給朋友，請他的 AI 幫他執行 git clone（複製）。clone 會在朋友的電腦裡建立一模一樣的專案資料夾，並完整保留與 GitHub 雲端的連線以及過去所有的存檔歷史。當朋友寫好新功能並 push 回雲端後，你只需要在自己的電腦請 AI 執行 git pull（拉取更新），就能瞬間把朋友寫好的新程式碼同步下載到你的電腦裡。就這樣「你 push ➔ 他 pull ➔ 他 push ➔ 你 pull」，徹底告別傳壓縮檔的石器時代！

🟡 協作小撇步： 因為 .env 沒有上傳到雲端，朋友第一次 clone 下來後，記得自己把一組測試用的 API 金鑰貼進他電腦的 .env 裡，程式才能順利跑起來喔！
