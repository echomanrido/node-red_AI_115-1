01 / 核心痛點解析

沒有 CI/CD 的 AI 開發：
一場無止盡的「打地鼠」輪迴

用 AI 寫程式的速度極快，短短幾分鐘就能做出一個個人記帳軟體。但隨著功能越疊越多，AI 往往在開發新功能時，不小心動到舊功能的共用邏輯。如果沒有自動化檢查，每次上線都要靠人工把整個網站從頭點到尾，既耗時又容易漏掉隱藏 Bug。

🔵 核心觀念：CI/CD 是 AI 軟體工廠的「自動品管與物流線」

CI（持續整合）負責在程式碼合併前「自動驗貨，確保沒改壞東西」；CD（持續交付 / 持續部署）負責在驗貨通過後「自動打包並上架到雲端」，讓你專注在創意與產品設計，把重複性的品管交給機器。

🔨

沒有 CI/CD 的日常

  • 叫 AI 加「匯出報表」，結果「新增記帳」按鈕壞掉了
  • 修好新增記帳後，總金額計算又出錯（打地鼠循環）
  • 每次更新都要手動打包、上傳伺服器，心驚膽戰
結果：越寫越慢，不敢改動舊程式碼
🛡️

導入 CI/CD 的工廠

  • 每次開 PR 自動啟動雲端體檢，秒抓型別與邏輯錯誤
  • 自動跑完所有舊功能測試考卷，保證「做 A 不壞 B」
  • 亮綠燈合併後，平台自動將最新版網站無縫發布上線
結果：放心讓 AI 衝刺，品質穩定可控
02 / 互動式架構流水線

以「記帳軟體」為例：軟體開發完整五步驟

點擊下方 SVG 流水線中的任意節點（步驟 1 至 5），查看每個階段在 GitHub 與雲端部署平台發生的詳細動作！

📘 名詞小百科：CD 的兩種意思「持續交付」vs「持續部署」

📦 持續交付（Continuous Delivery） 程式碼通過 CI 並打包好，隨時處於「可上線狀態」，但最後一刻保留人工點擊確認按鈕（例如大型金融或 App Store 審核前）才正式發布。
🚀 持續部署（Continuous Deployment） 全自動化無人值守！只要合併進 main 主線，Render、Netlify 或 Vercel 立刻自動重新打包並推上正式網址，多數 Web 專案採用此模式。
03 / GitHub Actions 雲端沙盒與三道關卡

CI 的運作原理與三道基本關卡模擬器

CI 的本質是一份寫在專案 .github/workflows/ci.yml 的檢查清單（不會寫沒關係，直接叫 Claude Code 或 Cursor 幫你生成即可！）。每當開 PR 時，GitHub Actions 會在雲端租用一台全新的空白電腦，徹底排除本機殘留舊套件或暫存檔干擾，依序執行三道關卡：

runner: ubuntu-latest (全新空白雲端虛擬機)

互動體驗：切換程式碼情境，觀察 CI 如何攔截 AI 失誤！

關卡 1 lint & typecheck

程式碼品質與型別檢查

1. npm run lint：透過 ESLint 抓出 AI 寫程式的壞習慣，例如未清理的無用變數，或 React 中不當使用 useEffect 導致無限迴圈卡死瀏覽器的危險寫法。

2. npm run typecheck：確保資料格式一致。記帳金額應該是純數字 100，若 AI 誤傳純文字 "100元" 去做加法運算，TypeScript 會立刻攔截！

記帳金額型別安全驗證公式
$$\text{Total} = \sum_{i=1}^{n} x_i, \quad x_i \in \mathbb{R}\text{ (Number)} \neq \text{String}(\text{"100元"})$$
關卡 2 npm run test

自動化功能測試（標準考卷）

事先寫好一份「標準驗收考卷」，讓電腦在背景模擬虛擬用戶操作記帳軟體：例如依序輸入三筆支出（100 元、250 元、50 元），檢查系統加總是否精準等於 400 元。

PR 合併綠燈放行邏輯條件
$$\text{Merge Ready} \iff \text{Lint} \land \text{Typecheck} \land \text{Test} \land \text{Build} = \text{True}$$

只要新功能一不小心改壞舊的加總邏輯，考卷立刻不及格並退回修改！

關卡 3 npm run build

打包測試（組裝出廠驗收）

開發時我們看到的是一個個零散的元件與程式碼檔案；正式上線前，必須透過 npm run build 將所有檔案編譯、壓縮並組裝成瀏覽器看得懂的最終網站成品。

這關能確保所有零件都能順利拼裝起來（不會有少引入檔案、漏傳本地新建檔案或語法無法編譯的問題），避免正式發布後用戶打開網站卻一片空白！

🔴 遇到 CI 亮紅燈怎麼辦？AI 時代超省力除錯法

CI 亮紅燈並不是壞事，反而代表它成功幫你擋下了一個準備上線的 Bug！你不需要自己苦苦追查，只要點擊 GitHub PR 頁面紅燈旁的 「Details」 查看報錯訊息，或者更聰明一點：直接開啟 GitHub Connectors（讓 Claude Code / Codex 直接讀取該 PR 的 CI 失敗紀錄），跟 AI 說：「幫我看一下這個 PR 為什麼 CI 沒過並修好它」，AI 就會自動定位錯誤、修改程式碼並重新推送！

04 / 進階測試武器與雙層防線

當產品越來越複雜：進階 CI 武器與「雙層防線」思維

基本三道關卡能守住 80% 的常見錯誤，但如果你的應用牽涉到真實瀏覽器畫面操作，甚至內建了「AI 理財顧問」這類每次回答都不太一樣的功能，我們就需要升級武器庫，並在 CI 之上建立第二層防線！

進階武器 A E2E Browser Testing

🎭 Playwright 自動化瀏覽器測試

在雲端虛擬機裡真正啟動一個瀏覽器，模擬真人打開網址、輸入帳號密碼、點擊「匯出月報表」按鈕，確認畫面沒有白屏且按鈕確實有效。

⚖️ 關鍵取捨原則（避免拖慢開發速度）

瀏覽器測試跑起來較花時間，切忌每個小畫面都寫！建議只針對「流程已穩定且最核心關鍵」的路徑（如：會員登入、結帳付款、核心報表匯出）設定即可。

進階武器 B AI Evaluation

⚖️ LLM-as-a-Judge（AI 裁判測試）

如果你的記帳軟體內建「AI 理財顧問」，每次生成的建議文字都不固定，傳統死板測試派不上用場。這時可準備常見題庫讓 AI 回答，再派另一位「裁判 AI」依據原始帳目數據與評分標準打分數！

📐 裁判 AI 品質放行門檻公式（20 題題庫）
$$\text{Pass Rate} = \frac{1}{N}\sum_{k=1}^{N} \mathbb{I}(S_k \ge S_{\text{min}}) \ge \theta_{\text{threshold}} \quad (N=20)$$

若 AI 算錯花費總額或開始胡說八道，導致通過率低於門檻，CI 就會直接退貨！

終極心法：Double-Layer Defense

雙層防線架構圖：CI 之外的「獨立 AI 實機驗證」

CI 全綠燈只代表通過了「事先寫好的標準考題」；真實世界的操作充滿意外，因此還需要第二層實機把關！
🟢 實戰秘訣：為什麼要找「未參與開發的獨立 AI」做實機驗證？

寫程式的 AI 容易有「盲點」（就像自己改自己的考卷容易忽略錯誤）。透過建立驗證技能（例如使用 create verification skill），在合併 PR 前指派另一位全新的獨立 AI 扮演挑剔的使用者，實際開啟預覽網頁到處點擊、輸入極端數值並錄製截圖或操作證據。兩層防線都過關，你就能真正高枕無憂地按下 Merge！

雙層防線風險收斂模型
$$P(\text{Bug in Prod}) = P(\text{Miss}_{\text{CI}}) \times P(\text{Miss}_{\text{Agent Verification}})$$
