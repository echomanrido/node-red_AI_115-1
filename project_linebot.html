LINE Bot 開發者指南核心：發送 API 請求四大注意事項

發送 LINE Messaging API 請求時，若忽略官方規範，容易導致訊息重複發送、推播費用暴增或被系統強制限流。以下為官方工程團隊提醒之最核心原則：

1. Reply vs Push：費用控管與 Token 限制

Reply Message (被動回應) 與 Push Message (主動推播) 是最容易混淆的兩種機制：

比較維度Reply Message (/v2/bot/message/reply)Push Message (/v2/bot/message/push)
費用計費 完全免費（不扣官方帳號推播配額） 計入推播費用（超出免費額度需收費）
目標依據 必須使用 Webhook 傳來的 replyToken 使用使用者的 userId 或 groupId
時效與次數 只能使用 1 次，且時效極短（約 1 分鐘過期） 無時效限制，隨時可主動下發
重試限制 不可重試（失敗後該 token 立即失效） 可搭配 X-Line-Retry-Key 進行安全重試
黃金原則：能用 Reply 解決的問答場景，一律優先使用 Reply；僅有在工控警報定時巡檢、感測器異常越限等背景非同步通知時，才使用 Push！

2. 冪等性防重複扣款：X-Line-Retry-Key

在網路不穩定時，後端發送 Push 請求若發生逾時（Timeout），開發者往往會啟動 Retry 重送。但可能第一次請求早已被 LINE 伺服器成功處理，重送會導致使用者收到兩次重複訊息並被扣兩倍費用！

解決方案：附加 X-Line-Retry-Key 標頭

發送 Push API 時，在 HTTP Header 加上由客戶端產生的 UUID v4。LINE 伺服器會在 1 分鐘內記住此 Key。若收到相同 Key 的重試請求，LINE 保證只會發送一次訊息，且絕不會重複計費！ 

POST https://api.line.me/v2/bot/message/push
Authorization: Bearer {Channel_Access_Token}
X-Line-Retry-Key: 123e4567-e89b-12d3-a456-426614174000
Content-Type: application/json

3. 速率限制 (Rate Limit) 與指數退避處理

LINE Messaging API 設有嚴格的頻率限制。當短時間內發送大量請求時，伺服器會回應 HTTP 429 Too Many Requests：

  • 讀取重試時間：檢查 Response Header 中的 Retry-After（秒數）或 X-Line-RateLimit-Reset（重置時間戳）。
  • 切勿盲目立即重試：若收到 429 仍連續發送，可能導致整組 Channel 被暫時凍結。
  • 實作指數退避演算法 (Exponential Backoff with Jitter)：等待時間為 \(2^n \times \text{基數} + \text{隨機擾動}\)，給予伺服器緩衝時間。

4. Channel Secret vs Access Token

清楚區分兩大金鑰的職責，避免資安漏洞：

  • Channel Secret (最高機密，用於驗證來源)： LINE 平台在呼叫你的 Webhook 時，會將請求內容以 Channel Secret 透過 HMAC-SHA256 演算法計算出摘要，放在 x-line-signature 標頭。後端必須自行比對，以防駭客偽造請求！
  • Channel Access Token (操作權杖，用於發送請求)： 呼叫 LINE API 時置於 Authorization: Bearer <Token> 標頭。官方提供長期有效、短期有效及 Stateless 三種，建議實務開發使用長期權杖或搭配更新機制。

兩大實戰架構：Docker + n8n 與 Google Apps Script (GAS)

實戰方案 A：Docker + n8n + ngrok 本地 AI Agent 工作流

本地容器化部屬

n8n 是一款強大且高自由度的開源工作流自動化平台。結合 Docker 與 ngrok，能在本地電腦輕鬆架構出具備 AI 思考能力的智慧 LINE 機器人：

  1. Docker Desktop 快速啟動 n8n：建立 Volume 持久化資料庫，映射 Port 5678。
  2. ngrok 建立安全隧道：執行 ngrok http 5678，取得 https://xxxx.ngrok-free.dev 網址，填入 LINE Developers Console 的 Webhook URL 並點擊 Verify。
  3. n8n 工作流節點配置：
    • Webhook 節點：監聽 /webhook-test/line，接收使用者的發話事件。
    • 擷取 replyToken：在下一個節點中將 {{ $json.body.events[0].replyToken }} 暫存為全域參數。
    • AI Agent 節點：串接 OpenRouter / Google Gemini Chat Model，輸入使用者文字進行語意解析。
    • HTTP Request 節點：呼叫 https://api.line.me/v2/bot/message/reply，帶入 replyToken 與 AI 生成內容，完成零成本極速應答！

實戰方案 B：Google Apps Script (GAS) 零成本雲端全自動化系統

免伺服器 Serverless

無須自建主機、天然內建 HTTPS 網址與 Google 雲端生態無縫鏈接，為中小型工廠與設備告警系統的最愛方案：

  1. 建立 GAS 專案並實作 doPost(e)： 
    function doPost(e) {
  var data = JSON.parse(e.postData.contents);
  var replyToken = data.events[0].replyToken;
  var userMessage = data.events[0].message.text;

  // 1. 即時寫入 Google 試算表作為工業報修日誌
  var sheet = SpreadsheetApp.getActiveSpreadsheet().getActiveSheet();
  sheet.appendRow([new Date(), userMessage]);

  // 2. 呼叫 Gemini AI 產生專業故障排除指引
  var aiResponse = callGeminiAPI(userMessage);

  // 3. 回覆使用者 (被動 Reply，不扣推播點數)
  replyToLine(replyToken, aiResponse);
}
  2. 部屬為 Web 應用程式 (Web App)：設定存取權限為「所有人 (Anyone)」，複製生成的 https://script.google.com/macros/s/.../exec 填入 LINE Webhook URL。
  3. 多重生態整合擴充：可進一步搭配 Google Sites (協作平台) 內嵌看板，或利用定時觸發器 (Time Trigger) 定期檢查機台 D 暫存器數據並發出 Push 推播。
