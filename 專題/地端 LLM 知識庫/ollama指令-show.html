三大核心機制 SVG 視覺化圖解

圖解 1：硬體與權重結構

為什麼檔名是 e4b，但 parameters 卻顯示 8.0B？

量化格式：Q4_K_M (~5.5 GB VRAM)

Gemma 4 E4B 採用邊緣高效架構：8.0B（80 億）是整個模型檔案包含所有模組的「總靜態參數量」，而 E4B（Effective 4B）則是每次生成文字時實際參與核心推論運算的「有效激活參數量」，兼顧了多模態能力與消費級顯卡的推論速度。

圖解 2：Ollama 0.20.0+ 提示詞與輸出引擎

renderer 與 parser 如何運作？為何 TEMPLATE 只剩 {{ .Prompt }}？

template source: renderer_parser

早期 Ollama 依賴純文字的 Go Template 拼接對話標籤，但面對 Gemma 4 複雜的圖片/音訊多模態佔位符、Thinking 思維鏈標籤與 Tools 函式呼叫時容易出錯。因此 Ollama 0.20.0+ 改由原生 Go 程式碼模組（gemma4-small Renderer 與 gemma4 Parser）全權接管輸入封裝與輸出拆解。

圖解 3：內容定址儲存架構 (CAS)

FROM ...\blobs\sha256-4c27e0f5... 的零複製共享原理

類似 Docker Image Layer 機制

執行 ollama show gemma4:e4b --modelfile 時，你會看到 FROM 指向 Windows 本機資料夾下的一串 SHA-256 雜湊檔案。Ollama 採用類似 Docker 的內容定址儲存（Content-Addressable Storage）：模型名稱（Manifest）只是輕量級的設定指標，無論你基於 FROM gemma4:e4b 建立多少個專屬模型，底層都共同指向同一個 5.5GB 權重檔，完全不會重複佔用硬碟空間。

FAQ 01 • 效能與延遲優化

如何在 API 或對話中關閉 thinking 以提升回應速度？

從 ollama show 可知 Gemma 4 的 thinking default: true。雖然這能大幅提高寫程式與邏輯推理的準確度，但模型會先輸出數百個思考 Tokens 才給出答案。若你只需要快速翻譯或簡單分類，可在呼叫 Ollama Chat API 時傳入 "think": false（或在 CLI 輸入 /set nothink），即可實現秒回。

FAQ 02 • 採樣參數原理

為什麼官方預設 temperature 是 1，而不是常見的 0.7？

具備深度推理（Thinking）能力的現代模型（如 Gemma 4 與 DeepSeek-R1），如果在思考階段把 temperature 設得太低（如 0.1），模型容易在思維鏈中反覆打轉、陷入邏輯死胡同。Google DeepMind 實測建議搭配 temperature=1, top_k=64, top_p=0.95，讓模型在探索解題路徑時保有足夠的發散性，再透過 top_p=0.95 過濾掉離譜的詞彙。

FAQ 03 • 記憶體管理

context length: 131072 代表一啟動就會吃滿 128K 顯存嗎？

不會！ 131072 是模型架構支援的「理論最大上限」。Ollama 為了保護消費級顯卡不爆顯存，預設執行時的上下文視窗（num_ctx）通常僅配置 4096 或 8192 Tokens。當你需要分析整份長篇 PDF 或大型程式碼庫時，務必在 Modelfile 中明確設定 PARAMETER num_ctx 32768，否則超出預設長度的早期對話內容會被自動截斷遺忘。

FAQ 04 • Modelfile 避坑指南

自己寫 Modelfile 時，需要把 TEMPLATE {{ .Prompt }} 複製進去嗎？

千萬不要！ 只要你在 Modelfile 第一行寫上 FROM gemma4:e4b，Ollama 就會自動從基底模型繼承 RENDERER gemma4 與 PARSER gemma4。如果你畫蛇添足地手動寫入自訂 TEMPLATE，反而會覆蓋掉原生的 Renderer，導致多模態圖片輸入與 Thinking 標籤解析失效！
