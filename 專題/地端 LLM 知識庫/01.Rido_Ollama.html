為什麼 Context Length 用「Token」而不是「字元 (Characters)」計算？

大語言模型（LLM）並非逐字處理字母，而是將文字切分為 Tokens（如上圖不同顏色區塊所示）。例如圖中範例：252 個字元 (Characters) 經模型分詞後等於 53 個 Tokens。英文單字通常 1 個 Token 約等於 4 個字母（0.75 個單字）；而中文一個漢字約佔 1~2 個 Tokens。可利用官方工具 platform.openai.com/tokenizer 精確預估提示詞是否超出本機設定的 Context Length 限制！

RAG 實戰致命避坑：文件編碼對照實測（UTF-8 正常 vs ANSI 亂碼導致檢索失敗）

文件編碼是地端 RAG 最常踩的隱形地雷！透過實機測試深刻比對：正確 UTF-8 如何精準召回，以及 ANSI/Big5 亂碼如何讓旗艦模型直接回覆 I don't know。

必避隱形地雷
成功範例：正常 (UTF-8 編碼)
檢索命中 • 完美回答
問：Motor or Equipment Overheating... 思考 10s • 生成排錯 3 步驟

解析：文本採用標準 UTF-8 編碼，點開右側引用彈窗內容結構清晰無亂碼。向量嵌入（Embedding）特徵完全吻合，模型（gemma4:e4b）順利提取散熱、電壓電流與軸承排查三步驟。

失敗案例：異常 (ANSI/Big5 亂碼)
菱形問號 • I don't know
問：馬達/設備運行時溫度過高 (過熱) 回覆：I don't know

解析：文件以傳統 Windows ANSI (Big5) 儲存，被 Page Assist 以 UTF-8 讀取時整篇化為「菱形問號亂碼（Mojibake）」。特徵失真導致語意完全破壞，模型即便思考 10 秒也只能無奈回覆「I don't know」。

1. 亂碼成因分析

Windows 記事本歷史版本常將中文字預設為 ANSI (CP950) 編碼，但現代 Web UI 與地端 LLM 向量資料庫一律只支援 UTF-8 解碼。

2. 向量檢索鏈路崩潰

文件一旦變成亂碼符號，文字分塊（Chunking）與 Embedding 產生的向量全然失去語意，模型就算強行讀取段落也看不懂，因而判定無法回答。

3. 標準解決 SOP

上傳前務必在 VS Code 或文字編輯器中檢查右下角編碼，並選擇「以 UTF-8 編碼儲存 (Save with Encoding ➔ UTF-8)」，即可百分之百避免亂碼！

關鍵 JSON 屬性說明
  • response：模型生成的回答純文字，包含 markdown 粗體符號（如 **五股...**）。
  • stream: false：若設置為 false，代表關閉 SSE 串流，等待模型全部運算完成後以單一 JSON 物件整體返回。
  • context：投影片中一長串數字數組（如 105, 2364, 107...）。此為本次對話轉譯後的 Token ID 列表。下次發送請求時若附帶此 context 陣列，Ollama 即可擁有前次對話的短期記憶！
