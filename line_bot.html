LINE Bot 的運作機制與系統架構

LINE Bot 是一種透過 Channel Gateway Server (GW Server)，在客戶端系統的 Bot Server 與 LINE App 之間收發 JSON 格式數據 API 請求的機制。點擊下方節點可查看各元件詳細職責：

LINE App (用戶端)：當用戶加入好友、傳送訊息或封鎖時，訊號會先送往 LINE Platform 的 Talk Server；企業也能透過 API 將訊息經由平台推播回用戶的 LINE App。

LINE 官方帳號、Bot 與 Channel 之間的關聯性

管理後台 (OA Manager)

Bot (LINE 官方帳號)

以 LINE Official Account Manager 管理。當不使用 API 時，可單純透過後台設定歡迎訊息與自動回應；啟用 API 後則與 Messaging API Channel 連動。

Messaging API Channel

收發 Webhook 與訊息

當用戶傳訊、加入好友或封鎖時，平台會向此 Channel 設定的 Webhook URL 發送 Webhook event；Bot 則使用此 Channel 發行的 Channel Access Token 向用戶傳遞訊息。

關鍵重點：Provider 與 userId

跨 Channel 識別同一用戶

如果 Messaging API Channel 與 LINE Login Channel 隸屬於同一個 Provider 之下，則兩者取得的 userId 是完全相同的！且注意 LINE Login 設定完成後必須更改為「已公開 (Published)」狀態才算完成發布。

LINE Bot 核心術語表 (Glossary)

術語名稱 定義與說明
Bot Server 為了接收 LINE 所發出的請求（如加入好友、封鎖、來自用戶的訊息等），而架設於客戶端的伺服器。
Talk Server LINE Platform 中負責發送和接收訊息的伺服器。
Channel Gateway Server (GW Server) 用來將從 Talk Server 接收到的資訊發送到 Bot Server，或將從 Bot Server 接收到的資訊發送到 Talk Server，使用時必須經過 Channel。

Webhook URL Bot Server 的 endpoint URL。當用戶與 Bot 互動觸發 Webhook event 時，LINE 平台會向此 URL 發送 HTTPS POST Request。
Provider 提供服務的個人、企業或公司主體，在 LINE Developers 控制台中建立。不同 Provider 之間的 userId 不互通。

Chapter 02

使用 Webhook URL 接收請求時的注意事項 (A ~ H)

注意事項 A

考量安全性的 SSL/TLS 通訊環境

GW Server 與 Bot Server 之間必須使用對應 SSL/TLS 的 HTTPS 通訊環境。

不接受自我簽署憑證 (Self-signed certificate)，請務必使用受信任第三方憑證頒發機構 (CA) 認可的憑證。
注意事項 B

1000 毫秒 (1秒) 內回傳狀態碼 200

Bot Server 接收到請求時，請先非同步寫入佇列/記憶體並盡快回傳 HTTP 200 OK，後續商業邏輯再交由後端處理。

回傳標準必須在 1000ms (1秒) 以內。若超過 1 秒，系統將自動發送 Error Notification 警示郵件（需為 Certified Provider 並洽詢業務開啟）。
注意事項 C

Webhook 數位簽章驗證

為防止來自 LINE 以外的偽造請求，請以 Channel Secret 為密鑰，對 Request Body 進行 HMAC-SHA256 計算並轉為 Base64，比對是否與標頭中的 x-line-signature 一致。

注意：LINE 公司並未揭露 GW Server 的 IP 地址，請勿使用 IP 白名單驗證，務必使用簽章驗證。

G) 建議的請求處理步驟 & 簽章驗證範例

為什麼建議先回傳 200 OK 再做後續處理？因為確保在 1 秒內完成回應可避免高併發時觸發逾時錯誤。

1. 接收請求 (1秒內) GW Server 發送請求 → Bot Server 以 Webhook URL 接收請求。
2. 暫存並回 200 (1秒內) 寫入 DB / 記憶體佇列 (Queue) 等，並立即回傳狀態碼 200 OK 給 GW Server。
3. 簽章驗證 驗證 x-line-signature（不區分大小寫）。若不一致則直接廢除不處理。
4. 拆解多個事件 在請求的 events[] 陣列中分別提取各個 Webhook event。
5. 執行商業邏輯 針對各個事件（文字、加好友、解封鎖等）進行非同步處理與回覆。
webhook_handler.js (Node.js 實作概念範例) 
const crypto = require('crypto');

app.post('/webhook', (req, res) => {
  // [注意事項 B & G] 1000ms (1秒) 內立即回傳 200 OK
  res.status(200).json({});

  // [注意事項 F-3] 標頭名稱必須設定為「不區分大小寫」(Express req.headers 預設已轉小寫)
  const signature = req.headers['x-line-signature'];
  const rawBody = req.rawBody; // 必須為原始字串或 Buffer

  // [注意事項 C] 計算 HMAC-SHA256 數位簽章
  const expectedSig = crypto
    .createHmac('SHA256', process.env.CHANNEL_SECRET)
    .update(rawBody)
    .digest('base64');

  if (signature !== expectedSig) {
    console.warn('非法請求：數位簽章不一致，予以廢除！');
    return;
  }

  // [注意事項 F-1] 1 個請求可能包含多個事件，請使用迴圈處理並容許新屬性 (F-2)
  const events = req.body.events || [];
  for (const event of events) {
    processEventAsync(event);
  }
});

D 大規模訊息處理的考量

在剛開啟顯示搜尋結果、推出贊助貼圖、群發訊息後、媒體曝光、或午間/晚間至午夜高峰期，請求會極度集中。

  • 嚴禁對 GW 伺服器進行壓力測試（請在自家環境測試）。
  • 若 Bot Server 無法消化導致請求在 GW Server 大量累積並影響其他 Channel，LINE 將不得不刪除累積的請求。
  • 擁有百萬好友的帳號推播活動時，請分批傳遞或錯開傳遞時間。

F 防範系統故障的 3 個細節

  • F-1 單次請求含多個事件：同時間大量傳訊或加好友時，1 次 Webhook 請求的 events 陣列可能包含多個事件，請務必以陣列迭代處理。
  • F-2 容許新增 JSON 屬性：Messaging API 更新時可能會在 Webhook event 中新增欄位，JSON Parser 請勿設定為遇到未知欄位即報錯崩潰。
  • F-3 HTTP Header 不分大小寫：標頭欄位名稱大小寫可能不經通知變更（如 X-Line-Signature 或 x-line-signature），驗證時請務必忽略大小寫。

H GW → Bot 通訊錯誤通知

當 GW Server 發送請求至 Bot Server 發生錯誤時，LINE 會發送郵件或顯示於 Console 的統計錯誤頁。

• 適用對象：僅適用於 Certified Provider 下的 Channel（需洽詢業務開啟）。

• 收件人：登錄於 Channel 基本設定及 Admin 註冊的電子郵件地址。

• 查看路徑：Console > 統計資訊 (Statistics) > 錯誤資訊 (Errors)。

Chapter 03

發送 API 請求時的注意事項 (A ~ I)

A ~ C) Channel Access Token 的發行、自動更新與有效上限

呼叫 Messaging API 時必須在 Header 帶入 Authorization: Bearer {channel_access_token}。基於安全性考量，建議透過 API 發行短期 (Short-lived) 或指定效期 (v2.1) 的 Token，並建立後端自動更新與撤銷 (Revoke) 舊 Token 的機制。

🔄 Token 無縫輪替最佳實踐 (Backend Server 定期執行)：

階段 1：使用 Token A
有效期屆滿前，後端先呼叫 API 發行 Token B。
階段 2：切換至 Token B
確認 Calling Server 切換至 Token B 後，呼叫 Revoke API 取消 Token A。
階段 3：發行 Token C
Token B 到期前，發行 Token C 並取消 Token B。
為什麼要取消舊 Token？
因為可同時操作的 Token 數量有上限（30個），多伺服器共用時務必撤銷舊權杖。
Token 種類 發行方式 同時有效上限 超過上限時的系統動作 失效條件
Short-lived (短期 30 天) 由 API 發行 30 個 按照發行順序，使最舊的短期 Token 自動失效 超過有效期限 (2592000秒) / 超過上限 / 呼叫 Revoke API
Long-lived (長期無期限) 由 Console 手動發行 1 個 重新發行時，使現有的長期 Token 立即失效 重新發行 / 呼叫 Revoke API
User-specified expiration (v2.1) 由 API 發行 (JWT) 30 個 回傳 API Error，無法追加發行！ 超過有效期限 / 呼叫 Revoke API
注意事項 D

發送完成後的回應與 Request ID

成功時回傳 200 OK 與空 JSON 物件 {}；失敗時回傳包含 message 與 details 的錯誤說明（注意：失敗 Body 格式可能不經通知變動）。

// 請務必記錄 Response Header 中的唯一識別碼：
X-Line-Request-Id: f70dd685-499a-4231...
注意事項 E

API 請求重試與防重複發送

當遇到網路異常或 HTTP 500 錯誤需重試時，請在 Header 加入 UUID 格式的 X-Line-Retry-Key，避免用戶收到重複訊息！

Header 範例：
X-Line-Retry-Key: 123e4567-e89b-12d3-a456-426655440001

※ 為減輕故障時伺服器負載，請務必使用 Exponential backoff (指數退避演算法) 控制重試間隔。

注意事項 F

字數上限與 Rate Limit 速率限制

  • • 文字長度上限：單則文字訊息上限為 5,000 個字（超過會回傳 Length must be between 0 and 5000）。
  • • 超出速率限制：短時間大量請求會回傳 The API rate limit has been exceeded. Try again later.
  • • 嚴禁線上壓測：無論正式或測試帳號，請避免對 LINE 發送大量測試請求，負載測試請在自家封閉環境實施。

G) 回應 (Reply) 訊息 vs 推播 (Push) 訊息

Reply API (回應訊息)

針對用戶觸發的 Webhook event，使用事件內附帶的 replyToken 進行回覆。

  • 一定時間內未使用即失效
  • 請設定為即時回覆
  • 每個 replyToken 只能使用 1 次
Push API (主動推播)

無論是否有來自用戶的訊息，都可以在任意時間點，指定 userId、群組或聊天室 ID 發送訊息。

H) HTTPS 媒體規範 & I) 大量 Access 防護

H) 媒體資源必須使用 HTTPS (TLS 1.2 以上)： 發送 Image、Video、Audio、Imagemap、Template、Flex Message 時，物件內指定的 originalContentUrl 或 previewImageUrl 必須為 HTTPS over TLS 1.2 以上（符合 Apple iOS 指南方針），否則內容將無法正常顯示。
I) 防範 502 Bad Gateway (管理圖片/影片 URL 的伺服器)： 當向大量用戶群發含圖片/影片的訊息時，所有用戶端手機會瞬間同時造訪您的媒體伺服器。請務必配置 CDN 或 Load Balancer 負載均衡機制，並採分批逐步發送，避免託管圖片的伺服器因瞬間流量崩潰回傳 HTTP 502。
Chapter 04

LINE Login 驗證授權與帳號綁定機制

LINE Login OAuth 2.0 & OpenID Connect 標準 6 步驟

透過 LINE Login，企業網站或 App 可取得用戶的 userId，進而與企業會員 DB 建立關聯性（帳號綁定）。注意：若用戶使用外部瀏覽器以帳號密碼登入，用戶必須事先在 LINE App「我的帳號」中註冊電子郵件與密碼。

步驟 (1) 設定 Callback URL

於 Console 的 LINE Login 頁面設定驗證後的重定向網址。必須為 HTTPS，多個 URL 請以換行分隔（最多 400 行，每行不超過 1000 字元）。

步驟 (2) 導向授權 URL

產生唯一隨機的 state 值（防止 CSRF 跨站請求偽造，嚴禁使用固定值或易猜測值），將用戶導向 https://access.line.me/oauth2/v2.1/authorize。

步驟 (3) 重新導向並驗證 state

用戶同意授權後，頁面帶回 code、state 與 friendship_status_changed。後端務必先比對 state 是否與步驟 2 一致！

步驟 (4) 取得 Access Token

使用 code 向 POST https://api.line.me/oauth2/v2.1/token (application/x-www-form-urlencoded) 換取 access_token 與 id_token。

步驟 (5) 解析與驗證 ID Token

當 scope 包含 openid 時會回傳符合 OIDC 規格的 id_token。請以簽章與 nonce 驗證。※電話號碼與 Email 只能從 ID Token 解碼取得（電話號碼需另外申請權限）。

步驟 (6) 取得個人資料與綁定

或呼叫 GET https://api.line.me/v2/profile 取得 userId，最後將 userId 與企業會員 DB 的帳號建立關聯性。

LIFF (LINE Front-end Framework)

在 LINE 平台內啟動的 Web App 平台。可從 LINE 平台直接取得 userId、chatId 及 Token，開發與用戶資訊連動或代替用戶將訊息發送到聊天室的應用程式。

在 LINE Login 服務尚未公開 (Developing) 階段執行測試時，請先確認人員權限：
